# 复盘：2026-08-11 晚间 ~ 2026-08-12 早晨 批次发布全失败

> 日期：2026-08-12
> 影响批次：晚间 #787–#790、早晨 #791（GitHub Actions `足球自媒体批次发布` 全部 `failure`）
> 结论：根因有两层，key 占位符只是表象，更深的代码 bug 在 key 修好后才暴露。

---

## 1. 现象

- CI 日志：`publish` 步骤崩溃，报错
  `requests.exceptions.InvalidHeader: ... reserved character(s) in header value: '***'`
- 文章从未生成 → 发布步骤无文可发 → 整批 `failure`。
- 午间批次（#784–#786）此前「成功」，是因为靠 qwen 兜底（见下文），并非真修好。

---

## 2. 根因（两层）

### 第 1 层：`HY3_API_KEY` 是占位符 `***`

- `constants.py` 原逻辑：
  `HY3_API_KEY = os.environ.get("HY3_API_KEY") or os.environ.get("DEEPSEEK_API_KEY", 默认key)`
- workflow 里写的是 `HY3_API_KEY: ${{ secrets.HY3_API_KEY || secrets.DEEPSEEK_API_KEY }}`。
- `HY3_API_KEY` secret 未建（或也是 `***`），回退到旧 `DEEPSEEK_API_KEY`，而它已被设成 `***`。
- 非空字符串 `***` 被当成真 key 注入 `Authorization: Bearer ***`；`*` 是 HTTP 保留字符，`requests` 在发请求前直接抛 `InvalidHeader`，LLM 调用根本没发生。

> 为什么午间看似成功：那时 `DEEPSEEK_API_KEY` 还是真实 DeepSeek key，代码拿它打 TokenHub → 401 → 自动降级到 qwen-turbo 兜底（旧 fallback 实际是“真主力”）。用户把 `DEEPSEEK_API_KEY` 改成 `***`、又切到 `HY3_API_KEY` 变量后，链路断裂。

### 第 2 层（真凶）：`rewrite_article` 丢弃了已匹配到的源文

- `generate_article_with_retry` 对转会/八卦类话题，会从 `transfer_news`/`news_articles` **懒加载（爬取全文）** 得到 `source`，再传给 `_rewrite_with_retry`。
- 但 `_rewrite_with_retry` 调用 `rewrite_article(topic, match_context, ...)` 时**没把 `source` 传进去**；`rewrite_article` 内部又用 `_find_source_article(topic, match_context)` 重新查。
- 此时 `match_context` 里的源文尚短（<100 字，爬取结果没写回），重新查询返回 `None` → `rewrite_article` 返回 `None` → `❌ 最终失败: 改写失败` → 0 篇文章。
- 这本是旧 bug，但之前在更早期的 `InvalidHeader` 阶段就崩了，**从未暴露到文章生成这一步**；key 修好后立刻踩中。

## 4. 验证结果

- 本地复现：占位符 `***` 下 `HY3_API_KEY` 正确回退到默认有效 key，`call_llm` 真实调通 hy3（HTTP 200）。
- 代码单测：`_rewrite_with_retry` 在「`match_context` 源文短、但已传入完整 `source`」场景下，修复前返回 `改写失败`、修复后成功生成 524 字文章。
- **线上端到端**：重跑今早 morning 批次（run `#31557323514`）结论 `success`，
  发布步骤 `发布完成! 发布 2/2 篇`，头条号返回 `Status 200 / 保存成功 / pgc_id 7672969020815000099`，
  实际发布 2 篇：《20岁高桥仁胡拒训背后：基尔挖角有多狠》《罗马想租乌多吉？这操作像极了凑满减》。

## 5. 后续建议

1. **Secret 管理**：`HY3_API_KEY` 已设真值，换 key 只需改 secret，无需动代码；`DEEPSEEK_API_KEY` 已废弃删除。
2. **兜底逻辑**：文章生成的 qwen 兜底目前只在 HTTP 401/402/403/404 触发；若 hy3 返回非 JSON（解析失败），不会兜底。如后续再遇“生成 0 篇但不是 key 问题”，优先查 `rewrite_article` 的源文匹配与 JSON 解析。
3. **幂等标记**：失败批次若已把某 batch 误标 `completed`，重跑前需先清空 `metadata.json` 对应标记，否则会被跳过。
