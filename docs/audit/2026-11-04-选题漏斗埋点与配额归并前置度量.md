# 选题漏斗埋点：给 S2（配额归并）先装上仪表

日期：2026-11-04　｜　性质：只加埋点，**没有动任何配额/阈值/闸门**

## 一、为什么先做这个，而不是直接合并配额

复杂度体检的结论是「审核太多、验证太少」，其中一条可执行项是 S2：
**把四套同时回答「今天写什么类型」的配额收成一套**。四套分别是：

| 配额 | 在哪 | 管什么 |
|---|---|---|
| `supply_mix` | 三层供给 | 一级·确定性 30% / 二级·突发 50% / 三级·软性 20% |
| `content_mix` | 月度配比 | 热点球评 45 / 数据对比 30 / 排行榜 18 / 战术榜单 4 / … |
| `batch_mix` | 每批结构 | main（热点球评）+ data（数据型）两槽，按目标缺口选型 |
| `topic_category` | 类别优先级 | 转会官宣 > 冲突舆情 > 中国足球 > 未分类 > 战报比分（单批上限 1） |

这四套能同时活着，是因为它们作用在漏斗的不同位置上；但**没有任何一条记录能回答
「这一篇是被哪一层挡掉的」**。「为什么今天只发了 1 篇」只能靠人肉翻日志。

在这种状态下直接删配额，等于凭直觉删闸门 —— 10-25 清 22 项僵尸测试的教训是：
删完才发现有几项其实还在拦（先查「被测符号是否还存在」才没删错）。
**所以这轮只装仪表，不动配额。** 一周真实数据出来再决定砍哪三套。

## 二、漏斗的定义

```
llm ──▸ dedup ──▸ material ──▸ category ──▸ batch_mix ──▸ slot ──▸ generated ──▸ final
```

| 层 | 含义 | 归属 | orchestrator 位置 |
|---|---|---|---|
| `llm` | LLM 原始返回的候选数 | 题源 | L751 |
| `dedup` | 批内/跨批/昨日/事件指纹/近 7 天 五道去重后 | 去重层 | L852 |
| `material` | 素材充分性过滤后 | 事实层 | L862 |
| `category` | `topic_category` 战报比分单批软上限裁剪后 | topic_category | L867 |
| `batch_mix` | 每批结构选定后（其余进 skipped） | batch_mix | L5284 |
| `slot` | 确定性供给/隔夜战报/多切口占位后，主稿真正拿到的槽位 | supply_mix | L5525 |
| `generated` | 主稿实际成稿（差额 = 源文预检跳过 + 生成失败 + 熔断） | 生成层 | L5535 |
| `final` | 本批成稿（**不含预测稿**） | 蓄水池/突发 | L5711 |

`dedup` 层的 detail 会拆成「批内 / 跨批次 / 昨日关键词 / 事件指纹 / 近 7 天关键词」五项 ——
否则「去重吃掉一半」这句话查不出是哪一支，等于没归因。

## 三、三条口径（都是踩过的坑）

1. **未调用记「缺失」，不记 0。** 某批没有确定性供给，`slot` 就没被记录。
   写成 0 会被读成「这一层吃掉了全部候选」，是 10-24「缺列当 0」事故的同款错误。
   实现上：`stages` 里没有这个键；`articles` 在没记 `final` 时是 `None` 而不是 `0`。
2. **数字变大也记，叫 `gain` 不叫负损失。** 蓄水池补位会让 `final` 大于 `generated`。
   把增量和损失混在一列加总，「净损失」会同时掩盖两层各自的动作。
3. **空台账 ≠ 零损失。** 埋点刚接上时台账是空的，报告必须说「**未判定**」，
   不能打印「各层损失 0 篇」—— 那会被读成「漏斗很顺」。
   验收脚本此时返回 **2**（未判定），不是 0（通过）。

## 四、它不是闸门（这一条写进配置了）

`topic_funnel` 没有任何阈值、不做判定、不阻断任何流程，所以：

- **不进 `pre-publish`**。把「不发这一批」绑在一个纯观测项上是倒退。
- 埋点函数 `_funnel()` 用 `try/except` 包住 `stage()`：层级名拼错会**大声打日志**
  （`⚠️ 漏斗埋点异常（llmX，不影响发布）`），但稿子照发。
- `stage()` 对拼错的层级名**故意抛 `ValueError`**：静默忽略拼写错误正是
  11-04「假接线」的成因（`_img_topic` 找 `c["source_images"]`，字段真实长在
  `c["fixture"]["source_images"]` —— 函数在、调用在、单测绿、数据恒空）。

它登记进了 `config/audit_tiers.yaml`（`code-change` + `weekly`，`kind: advisory`），
带真负向：验收脚本会**真的把源码里的 `dedup` 埋点改名**再跑一遍检查，必须报红；
再把首参换成变量，也必须报红。两条都过才算通过。债务基线不动（43 项 / 13 项有负向 / 债务 30）。

## 五、一周后怎么读这份报告

```bash
python3 topic_funnel.py --summary --days 7
python3 scripts/verify_topic_funnel.py --report --days 14
```

```
选题漏斗（近 7 天，21 批）
  配额请求 42 篇 → 成稿 29 篇（缺 13 篇，达成率 69%）
  LLM 候选    批均  3.8 篇   —             〔题源〕
  去重        批均  3.4 篇   -9            〔去重层〕
  素材充分性  批均  3.2 篇   -4            〔事实层〕
  类别软上限  批均  3.1 篇   -2            〔topic_category〕
  批次结构    批均  2.0 篇   -23           〔batch_mix〕
  可用槽位    批均  1.4 篇   -13           〔supply_mix/确定性〕
  主稿成稿    批均  1.2 篇   -4            〔生成层〕
  本批成稿    批均  1.4 篇   +4（补位）    〔蓄水池/突发〕
  ⇒ 最大损失层：批次结构（batch_mix），吃掉 23 篇，占全部损失的 42%
  注：这是观测值，不构成「该删哪一层」的结论 —— 合并配额前要同时看该层的拦截是否都是真拦截。
```

（以上是**格式示意**，数字是本机模拟出来的；真实数字要等一周。）

读法（三条判据，先定下来再看数，避免看到数再编故事）：

| 现象 | 含义 | S2 该怎么做 |
|---|---|---|
| `batch_mix` 吃掉最多 | 不是配额太松，是**候选本来就只有 2-3 条**，2 篇的结构刚好把它榨干 | 不动 batch_mix，问题在题源 → 该加的是供给 |
| `slot` 吃掉最多 | 确定性供给/战报在挤占主稿位 | supply_mix 的三层比例要重定，而不是删 |
| `dedup` 吃掉最多 | 五道去重里有重复劳动（昨日关键词 / 近 7 天 / 事件指纹 三者在做同一件事） | 这才是能真正合并的一层 |
| 全层损失都小但成稿仍少 | 问题不在选题漏斗，在**发布侧**（成稿≠发布，10 月 38%） | 转去查 `publish_ledger` |

**注意最后一行**：这条漏斗只覆盖「选题 → 成稿」。成稿 → 实发是**另一条漏斗**，
由 `publish_ledger` 记（10 月成稿 242、实发 93）。两份台账别混着看，
否则「成稿数」会再次被当成「发布量」（这是已经吃过一次的亏）。

## 八、踩到的一个坑，值得单独记

「不是闸门」这一项**首版是全文找 `pre-publish` 字样**，结果被 `audit_tiers.yaml`
里那句「不要把它挪进 pre-publish」判成红 —— 检查器把自己的注释当成了证据。
改成按 yaml 结构读 `tiers` 才对。

这就是全仓那条老纪律的又一次复现：**判定必须看结构/语境，不能裸匹配文本**
（闸门判词「关注」不能裸匹配、禁令类校验要用 AST 查真实 Call 节点，都是同一件事）。
已加成回归用例：`tests/test_topic_funnel.py::TestNotAGate::
test_presence_of_word_in_why_is_not_a_red`。
