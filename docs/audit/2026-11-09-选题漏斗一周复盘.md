## 二、先修两个口径坑，否则数字是错的

### 1. 命令参数：`--report` 不存在

任务给的 `topic_funnel.py --report --days 7` 会直接报
`unrecognized arguments: --report`。实际参数是 **`--summary`**
（另有 `--json` / `--selftest`）。等价的权威入口是：

```bash
PYTHONPATH=. /usr/bin/python3 topic_funnel.py --summary --days 7
PYTHONPATH=. /usr/bin/python3 scripts/verify_topic_funnel.py --report --days 7
```

两者输出一致，已交叉验证。

### 2. 台账里有重跑，直接汇总会重复计数

16 条记录对应 **13 个唯一「日×批次」**：

- `2026-11-05 晚间` 出现 **3 次**
- `2026-11-06 午间` 出现 **2 次**

同一批次重跑不是多写了文章，是同一批的多次尝试。所以下面**两个口径都列**，
不藏任何一个：

| 口径 | 批次数 | 请求 | 成稿 | 达成率 |
|---|---|---|---|---|
| 原始（脚本默认，含重跑） | 16 | 34 | 27 | 79% |
| 去重（日×批次只取最后一次） | 13 | 28 | 25 | **89%** |

判据表是在跑数**之前**定的，这里不改判据；去重口径只是把「重跑」这个测量
artifact 去掉，不是换标准。

## 五、S2 为什么不合并：三条证据

### 1. 去重层 7 天零损失

16/16 批 `dedup` 层剩余数等于 `llm` 层剩余数，损失合计 **0**。
8 条带明细记录的四个判据分支全部为 0：

```
同场 0 / 同事件 0 / 同标题 0 / 弱判据告警 0
```

「弱判据告警」也是 0 —— 意味着连**差一点被误杀**的候选都没有。合并这一层能
救回的篇数是 0。

### 2. 归并已经做过了

`dedup.py` 只有一次提交（`31cb6e0`，2026-11-06 14:14），进来的时候就是收敛后的
形态：**5 道 → 2 道硬判据 + 1 道告警**。

```
原来：批内关键词40% → 跨批次4判据 → 昨日40% → 7天事件指纹 → 7天关键词50%
现在：hard1 同场（对阵键+赛果指纹）、hard2 同事件（event_key）、warn 关键词重叠
```

原计划要并的「昨日 / 近7天 / 事件指纹」三道关键词重叠过滤，就是这次删掉的三道。
**再做一次归并，等于把已经删掉的东西再删一遍。**

### 3. 「零」不是假零（已排除空库误判）

`get_topic_history` 读的是 `output/<日期>/metadata.json` 近 7 天，而
`.gitignore` 里是 `output/` 加 `!output/**/metadata.json` —— **metadata 是入库的**。
CI 全新 checkout 也能读到历史，不是空库导致去重无从命中。

历史样本量也对得上：11-05 起每日 metadata 累计 7 / 4 / 4 / 5 / 2 篇。
所以这个 0 是「真的没重复」，不是「拦不到」。

## 七、配额反事实：改了会怎样（结论是都别改）

### 候选 1：`BATCH_QUOTA.normal_max` 2 → 3

| 项 | 现状 | 改后 |
|---|---|---|
| 单批上限 | 2（晨/午/晚） | 3 |
| 日上限 | 6 | **9**，突破 `daily_max: 8` 纪律 |
| 可回收 | — | batch_mix 未选 13 次里的一部分，最多把日成稿从 5.0 抬到 7~8 |

**不建议**：要改就得同时改 `daily_max`，等于动策略手册第五章的日更 6-8 条；
而且它会把「结构丢弃」变成「多写」，内容类型配比会更贴近 LLM 的自然分布
（历史问题是战术榜单占比冲到 44%）。

### 候选 2：下调 `supply_mix.TARGET_RATIO` 的一级占比（30/50/20 → 20/60/20）

| 项 | 数值 |
|---|---|
| slot 层损失 | 5 篇（去重口径），其中确定性占位 4 次、战报 3 次 |
| 实际一级占比 | **18%**（22 篇样本，低置信：metadata 是生成记录、非全量），已低于目标 30% |

**无效改动**：目标已经在实际值之上，再往下调不会改变任何一次分配决策。
这条正是 11-04「规则与阈值相斥」的同款陷阱——调了配置，行为一点不动。

> 18% 这个样本量偏小、口径也偏（`metadata.json` 按日累加但不是全量发布），
> 只用来判断「目标值在上还是在下」，不用来下比例结论。要准的数据应取
> `supply_mix` 每日产出，那是下一步的事。

### 候选 3：上调一级占比（30 → 40）

**负收益**：slot 层损失会从 5 篇变大，因为确定性供给每多占一个槽，主稿就少一个槽。

三个候选，两个无效或负收益，一个突破日更纪律。**配额不动。**

## 八、本轮落地：修掉两处「有数据、没证据」的观测缺陷

两处都是同一类毛病：**指标在，但指不到原因**。都不碰配额逻辑。

### 1. `generated` 层补失败原因分布

新增 `failure_taxonomy.py`，把失败串按**代码自己的错误字面量前缀**归类（闭集，不是模糊匹配）：
熔断 / 预检跳过 / 源文缺失 / 数据源不可用 / 事实闸门 / 反洗稿 / 标题评分 / 诱导话术 /
改写异常 / 改写失败。

三种兜底刻意分开，不合并：

| 类别 | 含义 | 为什么不合并 |
|---|---|---|
| `原因缺失` | 失败但没带 error 串 | 是**漏记**，不是「其他原因」 |
| `其他` | 有串但不认识 | 说明出现新文案，**该补词表** |
| 正常类别 | 命中闭集 | — |

接线：`_generate_articles_from_topics` 把原始 error 另存到 `stats["failure_errors"]`
（`issues` 里带「第N篇(类型)」前缀，拿去归类会被带偏），漏斗按本批切片后统计。
单测 **16 项**，其中一条是 AST 接线断言 + 负向（把关键字删掉必须判红）——
防的是「函数在、调用在、数据恒空」那种假接线。

### 2. `final` 层补「落盘」口径

`final` 原先记的是**落盘前**的内存篇数，出口合规逐篇丢的文章也算在里面（11-06 实证丢 1 篇）。
改成 `save_articles_local` 之后记录，同时留三个数：`内存 / 落盘 / 落盘剔除`。

`articles` 仍是内存口径（否则相邻层损失算不通），`落盘` 单独汇总、单独一行报；
老记录缺这个键就如实写「覆盖 N/M 批、不做差」，**不拿 0 冒充**。

单测 **5 项**（含「落盘为 0 是有效值，不能被 None 判定吞掉」「部分覆盖不做差」）。
