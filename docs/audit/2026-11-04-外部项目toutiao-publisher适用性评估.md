# 外部项目评估：ianx52/toutiao-publisher 是否适用于本项目

评估日期：2026-11-04
评估对象：https://github.com/ianx52/toutiao-publisher （v3.13.0）
评估方法：抓取全部 4 个文件 + GitHub API 元数据 + 用本项目 930 条真实成稿数据反算它的核心假设

---

## 一、结论（先行）

**不建议引入这个项目。** 它不是代码，是一份写给 AI Agent 看的操作手册（4 个 Markdown，无一行可执行代码、无一个 CSS 选择器）；
它解决的问题（"文章写好之后，怎么在编辑器里排版、配图、点发布"）与我们无人值守的流水线不在同一个问题上。

**但有三条真收获**，按价值排序：

1. **它指出了我们的一个真空白**：它有 20 条"发布前/后检查清单"，全部作用在**正文层**（段落长度、小标题编号、配图位置、手机端预览）；
   我们 41 项审核**没有一项**管正文结构，930 条成稿记录里**本地正文留存 0 条**。想做任何正文层改进，手上都没有语料。
2. **它逼出了一个更尖锐的判断**：我们真正卡住的不是"完读"，是"点击"。自算 CTR 中位 **0.27%**（曝光中位 2840 → 阅读中位 7）。
   它的全套规范作用在"点进来之后"，就算 100% 照搬，阅读量也不会动。
3. **可提炼 6 条结构判据**（见第六节），但建议等「正文留档」做完再决定是否升为闸门——现在连验收对象都没有。

**这不是"一个项目"，是"一套 Prompt 文档"。** 作者的作用是把他做 AI 时评号的经验写成 agent 可读的操作手册；

**这三条恰好是我们项目的全部内容。** 它做的是第 4 段（发布执行），我们做的是第 1、3 段加半个第 4 段。

## 三、定位对照

| 维度 | 它（toutiao-publisher） | 我们（football-auto-publish） |
|---|---|---|
| 形态 | Markdown 操作手册，供 agent 对话中执行 | Python 流水线 67k 行 + 42 项审核 + GitHub Actions 定时 |
| 运行方式 | 人在场，AI 逐步点浏览器，失败可人工兜底 | **无人值守**，每天定时跑，出错只能靠告警和台账 |
| 发布通道 | Playwright 点 DOM（无稳定选择器） | Playwright + **`/mp/agw/article/publish` API 直调兜底** |
| 配图 | AI 生成简笔插画（IP 角色「小黑」） | 真实图源：战报正文 `source_images` → 维基条目 → Commons → Pexels 白名单 → 卡片兜底 |
| 内容来源 | 作者自己写 | LLM 选题 + 采集 + 事实卡 + 12 层闸门 |
| 闭环 | 发布完记录 ID 就结束 | 发布台账 → 导出回流 → 绩效 → 配比调整 |
| 规模 | 单账号、日 1-2 篇、有人盯着 | 单账号、日 2-6 篇、30 天成稿 200 篇 |

**根本差异**：它靠"AI 现场看图判断"吸收页面变化，代价是必须有人在场；我们的流水线必须能在无人纠正的情况下跑完，
所以每一环都要有确定性判据和兜底。把它的做法搬进 CI，等于把"人兜底"换成"没有兜底"。

## 四、逐条裁决

### 4.1 不适用（不建议搬）

| 它的内容 | 为什么不搬 |
|---|---|
| **浏览器 DOM 操作 9 步 / 微头条 7 步** | 全文无选择器，只有「通常在页面底部或右上角」。我们 `publisher.py` 是跑了几个月、有 API 直调兜底的实现；换成一个"通常/可能"的指南是降级 |
| **排版规范（字号 16px / 行距 1.8 / 左边框 4px / 圆角 8px）** | 我们走编辑器粘贴与 API 提交，**字号行距由头条编辑器渲染，不受稿件控制**。这些数值在我们的链路上无处施加 |
| **颜色系统（红 #E53935 / 橙 #FB8C00 / 蓝 #1E88E5 三色）** | 同上，富文本粘贴后颜色由平台清洗；且足球资讯用三色标记体系与读者预期不符 |
| **AI 生成插画配图（seedream，每篇 5-6 张）** | ① 足球资讯读者预期真人照，简笔 IP 插画会削弱可信度；② 每天 10-36 张生图调用的成本与延迟；③ 我们已有 `cover_card` 生成兜底 |
| **「配图无真人肖像、不用真实人物照片」** | **与本项目策略直接冲突**（`source_images` 抓战报图、维基球员照）。此为体育新闻通行做法，未找到头条因此限流的证据。这条不采纳，但值得记一笔：若将来收到肖像权投诉，这是第一个要回退的点 |

### 4.2 我们已经覆盖（零增量）

| 它的主张 | 我们的实际情况 |
|---|---|
| 标题 **20-30 字** | 930 条成稿标题中位 **24 字**、均值 23.8，**85% 已落在该区间**。分桶看阅读差异也微弱（20-25 字中位 7 / 25-30 字中位 8），说明标题长度不是变量 |
| 发布后记录文章 ID 与时间 | `publish_ledger` 三层写入 + `bind_platform_ids` + `_first_pgc_id`，比它的模板严格 |
| 发布失败重试 3 次 | `publisher` 已有重试；且 `publish_ledger` 会记 unmatched 而不是猜测 |
| 数据记录模板（24h / 7 天 / 爆款分级） | `growth_import` + `ingest_exports` + `weekly_review` 已实现，且是自动回流不是手工填表 |
| 分类与标签 3-5 个 | 已有 tags 生成（每篇 5 个） |
| 原创声明 | 已勾选 |

### 4.3 有真价值（见第六节）

它那 20 条清单里，**只有"正文结构"这一段是我们完全空白的**，而且这一段恰好不需要控制编辑器样式，只约束稿件内容：

- 每段不超过 3 行（手机端约 50-80 字）
- 小标题 4-10 字、编号统一
- 列表单项不超过 7 项
- 配图位置在小标题上方、密度 800-1000 字一张
- 每段加粗不超过 3 处
- 引用块不超过 3 行

## 五、用我们的真实数据反算它的假设

数据源：`output/*/metadata.json` 全部成稿记录（930 条，其中 622 条有绩效回流）。

### 5.1 标题字数（它的核心主张之一）

```
标题字数：中位 24，均值 23.8，范围 11-36
按字数分桶（n=622）：
  15-20 字  n= 75  中位阅读  7
  20-25 字  n=280  中位阅读  7
  25-30 字  n=226  中位阅读  8
  30-35 字  n= 36  中位阅读  6
20-30 字（它推荐区间）: n=526 中位阅读 8
区间外                : n= 96 中位阅读 6
```

**判定：假设在我们数据上不成立（或者说，早已被满足）。** 我们本来就在区间里，区间内外差 2 次阅读，
在曝光中位 2840 的量级上不构成变量。**照搬这条等于什么都没做。**

### 5.2 真正的瓶颈：点击率

```
曝光中位 2840  →  阅读中位 7
自算 CTR（reads/impressions，n=618）：中位 0.27%，均值 1.09%，P90 3.26%
```

1000 次曝光换来 2.7 次点击。**P90 是 3.26%，和 P50 差 12 倍**——说明不是"全都不行"，
而是一小部分稿子能进流量池、大部分完全进不去。这是「标题+封面的信息流表现」问题，
**不是"点进去之后是否好读"的问题**。

它整套规范（段落、小标题、配图位置、颜色）全部作用在点击之后。

### 5.3 配图与阅读的关系（顺带验证封面修复的紧迫性）

口径说明：`article.images` 为空即我们台账里的 `published_without_cover`。两者已交叉核对——
`publish_ledger_2026-11-04.json` 共 2 条记录，其中 1 条 `images=0`，`counts.published_without_cover` 恰为 1。
（930 条按 `(date, slug|title)` 去重后仍是 930，无重复记录，统计不受重复计数污染。）

```
有正文配图(≥1)  n=542  中位阅读 8  均值  99.7  曝光中位 2736
images 为空      n= 80  中位阅读 4  均值  20.9  曝光中位 3467
```

无图的稿子曝光更高（3467 vs 2736）但阅读只有一半——**配图缺失直接压在点击率上**。
另外：`10-25 之后` 的 40 条里有 **21 条 images 为空（52%）**，说明封面修复（11-04 完成）的效果还没进样本。
**在无图率还挂着 52% 的样本上评估任何内容层改造，都会得到被污染的结论。**

## 六、如果只搬 6 条，应该搬这些

这些判据的共同点是：**不依赖编辑器样式，只约束我们产出的 Markdown 正文**，因此可以被自动校验。

| # | 判据 | 它的原值 | 建议 |
|---|---|---|---|
| 1 | 单段字数上限 | 手机端 50-80 字 / 不超过 3 行 | 用**我们自己正文的段落字数分布 P75** 定，不直接取 80 |
| 2 | 最长段落 | 不超过 3 行 | 先只做"报告"：`content_stats` 加 `max_para_len` / `avg_para_len` |
| 3 | 小标题字数 | 4-10 字 | 取 4-14，先看分布 |
| 4 | 列表项数 | ≤7 | 直接可用（我们 `content_stats.bullets` 已统计，只是没判） |
| 5 | 配图密度 | 800-1000 字/张 | **与我们"零配图率 ≤5%"的现有指标合并成一条**，不新增指标 |
| 6 | 每段加粗处数 | ≤3 | 需要 `content_stats` 先统计 `**` 数量 |

**但落地前提是「正文留档」**：930 条记录里本地正文 0 条（`path` 指向 runner 临时目录 `/home/runner/work/_temp/...`，跑完即销毁）。
没有正文，这 6 条既无法验收、也无法做事后相关性分析（"段落短→完读高"到底成不成立，我们没有一分钟的证据）。

## 七、建议的执行顺序

1. **P0 · 正文留档**（前置，半天）：在保存成稿时把正文一并落进仓库（按 `output/<date>/articles/<slug>.md`，或只存 `content_stats` 摘要 + 前 200 字钩子）。
   没有这一步，后面所有内容层讨论都是空的。
2. **P1 · 先把点击率当主指标**：零配图率从 52% 压到 ≤5% 之后再取两周数据看重算的 CTR。
   若 CTR 仍 <0.5%，再去查封面卡片样式与标题钩子（那才是信息流层的问题）。
3. **P2 · 再决定要不要把 6 条判据升为闸门**：先用留档的正文算出真实分布，定阈值，再挂 advisory；
   **不要**先写死 80 字 3 行然后逼 LLM 遵守（那是把别人的尺子套我们的稿子，10 月"疑问收尾 85.5%"就是这么来的）。
4. **不引入**：本项目的任何代码路径都不接这个仓库。它没有代码，只有方法论；方法论里我们能用的部分已在第六节提炼完，
   剩余部分与我们的自动化前提冲突。
