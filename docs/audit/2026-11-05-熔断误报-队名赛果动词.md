## 二、根因：三层叠加

### 第 1 层 · 采集层切错了

`media_scraper.py` 从战报标题解析比分与队名，规则是「比分前 = 主队，比分后 = 客队，
去掉已知前缀」。标题是：

```
朗斯主场1-9被科莫血洗，法布雷加斯赛后一句话比比分还扎心
```

`1-9` 匹配上 → `home_score=1, away_score=9`，`before=朗斯主场`（去后缀得「朗斯」✓），
`after=被科莫血洗，…` → 命中前缀「被」→ `科莫血洗，…` → 取 2~6 个汉字 → **`科莫血洗`**。

`away_prefixes` 里收了「绝杀/点杀/逆转/爆冷/遭/被/力克/大胜/小胜/险胜/战平/逼平/
横扫/完胜/击退/斩杀/淘汰…」，**没有「血洗」**；队名尾部剥离表只有
「淘汰/淘汰出局/绝杀/出局/噩梦/点球/加时」，也没有。动词就这样留在了队名里。

本地实测（修复前）：

| 输入标题 | home_team | away_team |
|---|---|---|
| 朗斯主场1-9被科莫血洗… | 朗斯 ✓ | **科莫血洗** ✗ |
| 欧冠主场1-9惨败科莫！… | **欧冠** ✗ | **惨败科莫** ✗ |
| 科莫留力仍9-1狂胜朗斯 | **科莫留力仍** ✗ | **狂胜朗斯** ✗ |

### 第 2 层 · 校验层把它当成合法队名

`_looks_like_team()` 只用黑名单判「像不像队名」，而 `_TEAM_DIRTY_TOKENS` 同样漏了
「血洗」→ 判为合法 → `validate_article_vs_match_data` 硬要求**正文出现「血洗」**。

正文永远不会把「血洗」当队名写，所以每一版改写都必然被打回。**这是死循环。**

而 10-13 那次的「大田市民首发」还能靠「未登记队名的简称放宽」蒙混过去——
「血洗」两字恰好也不是登记队名，`_relaxed_team_mention` 取前 2 字仍等于「血洗」，
正文里没有这两个字 → 放宽也救不了。

### 第 3 层 · 熔断层按「次数」计，把局部问题放大成全批停摆

`_note_consistency_reject()` 每次调用 `count += 1`，`count` 达 5 即熔断。
同一篇的「重试 N 次 + 降级重生成 1 次」各自计数，于是一篇稿子点着了整个批次。

**这是与规则误报同等重要的设计缺陷**：任何一条错规则的后果都被它放大 5 倍以上；
反过来，只要修掉它，同类局部误报就不会再演变成全批停发。

## 三、修法：按结构清洗，不继续补词

赛果动词是开放集合（血洗/屠杀/吊打/零封/双杀/掀翻/狂胜/溃败/翻盘…）。历史上每
补一次只挡住下一次复发的那个词：10-13 补了「首发/替补/阵容」，11-05 又被「血洗」
打穿。所以改**结构性清洗**，词表只维护一份。

### 新增 `team_names.py`

```python
clean_team_name("科莫血洗")   # → "科莫"     粘连救回
clean_team_name("狂胜朗斯")   # → "朗斯"
clean_team_name("被科莫血洗") # → "科莫"     介词 + 动词一起剥
clean_team_name("血洗")       # → ""        整体是动词 → 不是队名
clean_team_name("拜仁慕尼黑") # → 原样       真队名一个都不许改
```

`RESULT_VERBS` 按长度降序（保证「大胜」先于「胜」），循环剥两端直到不再变化；
剥完不足 2 字即视为「整个字符串就是动词」。

### 四处接线

| 位置 | 改动 |
|---|---|
| `media_scraper._parse_match_from_link_text` | 返回前清洗 home/away（**从源头**产出干净队名） |
| `media_scraper._parse_zhibo8_report` | 同上（战报页标题解析） |
| `orchestrator._build_match_reference` | 多源校准返回清洗后的值，不再把脏串传给下游 |
| `orchestrator.validate_article_vs_match_data` | 先清洗再校验，脏值告警里同时打原串与清洗结果 |

关键取舍：**能救则救，救不回来才跳过**。
「科莫血洗」救回「科莫」后**仍然比对正文**（正文真没提照样拦截）；
只有「血洗」这种整体是动词的才跳过该项校验并 `print` 留痕。
不是「见到脏串就整场跳过校验」——那是拿少校验换绿灯。

### 熔断阈值改按「篇」计

```python
_CONSTISTENCY_REJECTS["subjects"] = []      # 打回过的选题
articles = len(subjects) or n               # 解析不出选题时退回按次数（宁停勿错）
auto_suspend_if_systemic(articles, detail=f"...打回 {n} 次、涉及 {articles} 篇选题...")
```

11-05 事故形态（同篇 5 次）→ 计 1 篇，不熔断；多篇同时失真 → 照常熔断。
熔断 history 的 detail 会同时写「N 次、涉及 M 篇」，一眼看出有没有放大。

## 四、顺带查出的第二处「台账自相矛盾」

修 Bug 时发现 `output/2026-11-05/metadata.json` 里：

```
articles:                   4 篇（今日累计：noon 3 篇 + morning 1 篇）
image_floor.articles_below: 0                      ← 只反映最后那 1 篇
```

3 篇各只有 1 张图，台账却说 0 篇不足。根因：合并动作在 **batch.yml 的两段内联
python** 里，两段都只合并 `articles` / `batches_completed`，`image_floor` 直接沿用
本批的值。

修法：
* 抽 `scripts/merge_metadata.py`，两处回写统一调用它，合并后**按合并结果重算**
  `articles_below` / `below_titles`（口径只写一处）；
* 新增 `image_ledger.py`（`has_image_ledger` / `count_below_floor`），判据是
  「这篇有没有配图台账（`image_cards` / `image_anchors` 两栏存在）」——改造前的
  老产物没有这两个键，不参与判定（**未判定 ≠ 通过**）。

12:21 的 noon 批 3 篇是版式库改造**之前**的代码产出的（每篇 1 张），15:13 的
morning 批才是改造后（3 张）。拿新尺子量改造前的老产物只会制造噪音——
那些稿子已经发出去了，判红也修不好。
