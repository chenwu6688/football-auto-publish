# 审核机制体检与四处修复（2026-11-04）

> 起于一个提问：「现在的审核机制是否合理」。
> 结论：**方向对、位置错**——它审「规则写得对不对」，很少审「稿子实际发出去没有、有没有人看」。
> 下面三处是查出来的洞，一处是对「是否过严」的数据回答。

## 一、铁证：一个稿子穿过三道审核

2026-11-04 午间这篇：

```
大罗VS C罗巅峰数据对决，谁才是真正的锋线之王？
```

| 环节 | 应然 | 实然 |
|---|---|---|
| 生成侧 | 疑问收尾限额已满，应打回 | 兜底放行（已于 11-04 上午修 `_swap_to_template_title`） |
| 验收侧 | `verify_publish_gate` 应报硬违规 | **报「零硬违规 ✅」** |
| 发布侧 | 不该发出去 | **12:xx 已发布**（`platform_id 7704162883977888290`），images=0 无封面 |
| 观测侧 | 无封面 57% 该告警 | 无人看 |

验收侧为什么判 ✅ —— 同一个标题，两套输入两个结论：

```
score_title_plan(不传 recent_titles) → 74 分，通过
score_title_plan(传 recent_titles)   →  0 分，违规（近 14 天疑问收尾已 2 篇）
```

`_score_titles` 复算时**不传历史标题**，疑问收尾限额这条规则**从来没触发过**。
它不是「判错了」，是「根本没判」——比没有验收更糟，因为它让人相信这条规则在工作。

**修法**：按篇的日期还原当时的历史（14 天窗口 + 同日已判过的按顺序累加，对应运行期的
`_SESSION_TITLES`）。不调 `recent_titles_for_gate`，因为它掺了「今天」和进程状态，
复算历史某一天会算出错的窗口。

修好后一次性暴露 56 条存量违规（86 条里），通过率从「看起来没问题」掉到 **22.1%**。

## 二、台账按天单文件 → 多批次互相覆盖

`publish_ledger_{date}.json` 是覆盖写，而一天有晨/午/晚三个批次。
11-04 就是：晨间 1 篇的发布记录被午间覆盖掉，「今天实际发出几篇」从台账上算不对。

**修法**：三层写入
- `publish_ledger_{date}_{batch}.json` —— 批次明细
- `publish_ledger_{date}.json` —— 当天聚合（`version=2`，含 `batches`）
- `publish_ledger_latest.json` —— 本次批次，兼容既有读取方

同批次重跑幂等（按 `(title, status, batch)` 去重），旧格式文件作为 `legacy` 批次并入。

## 三、没有任何验收在看「发出去没有」

38 个 `verify_*` 里，全都在审「该不该发」：
标题合不合规、篇数对不对、有没有图。**没有一条在审「发没发成」**。

11-04 午间 2 篇里 1 篇失败（`发布超时: 无API响应`），台账如实记了原因，**零告警**。

**修法**：新增 `scripts/verify_publish_success.py`
- 硬项：近 7 天成功率 ≥85%（每天 2 篇，7 天约 14 篇；90% 只容 1 次失败，偶发就会天天红）
- 硬项：**连续 ≥2 篇失败**必定拦——这是链路断了的信号，与比率无关
  （2 篇全败时比率 0%，20 篇败 2 篇时 90% 但属偶发，后者不该阻断）
- 硬项：失败必须带 `reason`（没原因的告警等于没告警，10-25 事故）
- 告警：台账覆盖天数（缺台账 ≠ 没发布，但三种可能都该看见）

当前实测：成功率 87.5%（7/8），缺 3 天台账（10-29~10-31），无封面 4/7。

## 四、六套标题尺子，其中两套方向相反

| 尺子 | 位置 | 判什么 |
|---|---|---|
| `_title_score` | 保存阶段选 title vs backup | 数字+3、巨星+2、**问号+2** |
| `score_title_plan` | 生成闸门（及格 60） | 综合 |
| `title_elements` | 三要素 | 数字/对比/专名 |
| `title_positive` | R11 加减分 | 悬念词/字数 |
| `title_antipattern` | 播报式 | 比分/赛事名开头 |
| `title_gate` | 疑问限额/锚点 | **禁止疑问收尾** |

`_title_score` 给问号 **+2 分**，`title_gate` 禁止疑问收尾。保存侧在奖励加问号，
闸门在拦问号，谁赢取决于 `backup_title` 有没有问号——这是「闸门说违规、稿子还是疑问收尾
发出去」的一条隐蔽通路。

**修法**：`_title_score` 改为调用 `score_title_plan`（同一把尺子）。
标题体系宁可少一套，也不要两套相反的。

## 五、「是否过严」：一处过严，一处不过严

### 不过严：疑问收尾限额（我一开始判错，数据推翻了）

先用我方 88 篇有绩效的稿子对比，得到「疑问收尾 vs 非疑问，中位阅读都是 7.0」，
据此以为限额过严。**这个结论是错的**——样本只有 88 篇且都是老稿。

去看头部账号的 181 条图文样本：

```
头部疑问收尾  5 / 181 = 3%
我方 11-02 后 4 / 14  = 29%
限额 2 篇/14 天 ≈ 7%
```

头部只有 3%，限额 7% 不仅不过严，还偏松。**规则方向对，是供给没跟上。**

疑问收尾占比的时间曲线也印证：6-8 月 10~30%（正常），9 月底~10 月冲到
**52% → 84% → 80%**（我们自己把 prompt 写歪了），11-02 新 prompt 后回到 29%。

### 真过严：赛果播报式的「比分在起首」

```
皇马3-1巴萨，第70分钟换人后连丢2球   → 判 0 分，理由「以比分开场」
```

这条标题数字、专名、过程俱全，是标准的好标题。规则一的定义是
「**只报结果、不报过程**」，那过程锚点天生就该豁免。

**修法**：`_hit_rule1` 加第四个豁免（过程锚点），复用 `title_features.has_anchor`
的唯一口径。验证三组：

```
皇马3-1巴萨                        → 仍拦（纯播报）
皇马3-1巴萨，第70分钟换人后连丢2球   → 放行（82 分）
3-1！皇马赢球                      → 仍拦（有赛果词无过程）
```

> 注意 `has_anchor` 是 `@property` 不是方法。写成 `has_anchor()` 会抛 TypeError
> 并被 `except` 吞掉——豁免静默失效，看起来"加了却没用"。这是本轮第二次踩
> 「静默吞异常」。

## 六、Unsplash 接入现状

用户提供 Application ID 960197 / Access Key。实测：

| 链路 | 结果 | 判读 |
|---|---|---|
| `api.unsplash.com`（走代理） | 401 | Access token invalid |
| `api.unsplash.com`（绕过代理） | 401 | 同上，排除代理篡改 |
| 随机 43 位串对照 | 401，**错误信息一字不差** | 不是抄错字符 |
| Key 长度/字符集 | 43 位、base64url 合规 | 格式没问题 |
| `images.unsplash.com` | 404（图不存在，但域名可达） | **CDN 链路是好的** |

结论：**Key 未生效，非代码问题**。Unsplash 新应用需在后台完成设置/同意 API 条款后放行。
CDN 通说明 Key 一旦有效，图就能下。

已做：Key 写入 `scripts/local_env.sh`（gitignore）；`data_collector` 的 Unsplash
失败不再 `except: pass`，401/403/429 按 `scraper_diagnostics` 分类落账并 `break`
（不拿无效 Key 浪费第二个 query）；新增 `scripts/probe_image_sources.py` 一条命令探活四条链路。

**Secret key 不入库也不需要使用**：本项目只调公开读接口（Client-ID 认证），OAuth 流程用不到。
截图里那个已明文外泄，建议 rotate。

## 七、生效日与三态

`GATE_SINCE = 2026-11-05`（验收器补上下文生效日）。

存量 56 条违规是真实的（不是误杀），但按既往教训，红超过两周一定会被人加 `|| echo`
软化，等于把刚修好的尺子又做松。处置：

- 硬项只判生效日之后的稿 → 真违规照样拦
- 存量数字在报告里**照实写**（`legacy_violations: 56`），不隐瞒
- `ok` 支持三态：True / False / **None（未判定）**；未判定时退出码 0 + `::warning::`，
  不做假绿灯
