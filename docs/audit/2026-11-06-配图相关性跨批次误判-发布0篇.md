## 二、这条报错有两个问题，都不是「配错图」

### 问题 1（今天 0 篇的直接原因）：它复验的不是本周转的产物

那篇《阿森纳客场2-1拿下斯拉维亚》是 **morning 批次 00:07 就已经发布出去**的（台账 `publish_ledger_2026-11-06_morning.json`，pid 7704843009002701350）。

它为什么在 noon 的复验范围里？因为步骤 11「同步已有批次元数据」会把仓库里的当日 metadata `cp` 到 runner，而当日 metadata 是**跨批次累计**的（步骤 28 合并）。于是 noon 的复验窗口里躺着 morning 的成稿记录，而它的 md 文件只存在于**生成它的那个 runner**——早随机器销毁了。

旧实现读不到文件就把 `body` 置空，然后：

```python
text = f"{art.get('title')}\n{art.get('content')}"   # content 是 ""
if not text.strip():                                  # 标题非空 → 不成立
    ...
# 继续走实体判定 → 拿标题当全部正文
```

标题里写的是「斯拉维亚」（简称），anchor 写的是「拉格斯拉维亚」（残缺名），判「实体不在正文」→ **假失败**。

这是本项目反复踩的同一个坑：**「返回空」必须区分「真没数据」与「被拦/拿不到」**。文件读不到属于「拿不到」，只能判未判定，绝不能退化成用标题冒充正文。

### 问题 2（真实缺陷，但不是今天的阻断原因）：残缺队名进了 anchor

直播吧给的队名是「拉格斯拉维亚」，少了「布」。`entity_map.json` 里登记的是「布拉格斯拉维亚」。

- `data_chart.resolve_team("拉格斯拉维亚")` → `None`（查不到，按约定不猜）
- `candidates` 的准入判断是裸 `"拉格斯拉维亚" in 正文`——而它**恰好是「布拉格斯拉维亚」的子串**，于是侥幸放行
- 画出来的图上印着「拉格斯拉维亚」——**图本身成了错误信息**
- 验收侧 `image_relevance.hits_all` 走别名集，判它「不在正文」

同一张图，绘图侧放行、验收侧拒绝。两边各写一套判据，必然对不上。

## 三、还有一处差点让两篇稿永久消失

查 metadata 时发现 `batches_completed: ["morning", "noon"]`——**noon 明明没发出去，却被标成已完成**。

写入点不在发布步骤，而在 `orchestrator.save_batch_state`：

```python
batches = existing.get("batches_completed", [])
if batch_name not in batches:
    batches.append(batch_name)      # ← 保存成稿时就写了「已完成」
```

它跟着步骤 28「生成完成元数据回写」进了仓库（提交 `e79a282`）。后果：幂等保护读到「noon 已完成」→ 兜底 cron 不重跑、人工补发被跳过 → 两篇稿永久丢。

11-05 晚间修过一次同类问题，但那一次只改了 workflow 的回写条件（`steps.publish.outcome == 'success'`），**没动生成侧**——规则写两处，改一处等于没改。

## 六、残留风险

1. **E 项判据仍只看「同 runner 上的文件」**。跨批次累计的记录永远判未判定，等于 E 只对「当批自产」有效。要真正做到跨批复验，得把正文随 metadata 一起提交（体积与隐私代价另算），或者只复验 `batch_name == 当前批次` 的记录。
2. **重跑失败批次会重新生成**。产物不落仓库，只能重跑生成。metadata 里上一轮的未发布记录需要人工清（这次手工删的），否则当日成稿数虚高；未加自动清理，因为判据不够硬（`platform_id` 至今大面积为空，无法可靠区分已发/未发）。
3. **`--unmark` 是运维口，不在自动化链上**。误标完成只能人工发现、人工解除。
