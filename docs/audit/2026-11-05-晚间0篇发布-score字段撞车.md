# evening 批次 0 篇发布：`score` 同名字段撞车把两条稿全丢了

**日期**：2026-11-05 19:25–19:29 · **run** `42018772288`（#1842）·
**结论**：3 篇选题 → 2 篇在「标题重拟」处崩掉（各重试 3 次）→ 仅剩 1 篇**预测稿**，
而预测稿本就不发头条 → 发布步骤「无可发布文章」exit 1 → 整批 0 篇。

## 一、真实失败链（三个环节，只有第一个是 bug）

| # | 环节 | 现象 | 性质 |
|---|---|---|---|
| ① | 生成文章 · 标题重拟 | `AttributeError: 'int' object has no attribute 'get'`（2 篇 × 3 次） | **真 bug**（本节） |
| ② | 生成文章 · 结果 | 只剩 1 篇，且是**预测稿** | ①的后果 |
| ③ | 发布到头条号 | `❌ 没有找到 evening 批次的文章 (目录为空)，中止发布` → exit 1 | ②的后果 + 语义缺陷 |

```
在 …/output/2026-11-05 中找到 1 个 article-*.md 文件: ['article-1-勒沃库森近5轮4-145b5c.md']
```

## 二、根因：`score` 一个名字两种东西

`title_brief.collect()` 里：

```python
sc = facts.get("score") or {}
hg, ag = _num(sc.get("home")), _num(sc.get("away"))
```

- 事实卡（战报）里 `score = {"home": 1, "away": 9}` —— 比分；
- **LLM 产出的选题**里 `score = 90` —— 选题**排序分**（见 `orchestrator.py` 的选题 JSON
  schema 与 `topics[i].get("score")` 排序逻辑）。

`90 or {}` 得 `90`（int 为真值），`90.get("home")` → `AttributeError`。

触发路径：标题评分不及格 → `repick_title()` → `title_brief.brief_text(topic)`
→ `collect(topic)`。**LLM 选题天然带 int `score`，所以这条路上必崩**；
战报选题（score 是 dict）不会崩 —— 这就是为什么昨天没暴露。

三处同型代码（`or {}` 兜底把 int 当成 dict）已全部加 `isinstance` 守卫：

- `title_brief.py:collect`（本次炸点）；
- `orchestrator._build_recap_fact_card`（战报卡）；
- `orchestrator` 战报选题入口。

另修同形状的 `goals`（可能是「总进球数」int，而不是进球事件列表）、
`home_standing` / `away_standing`（可能是排名 int）、`keywords_cn`（可能是 int）。

## 三、比 bug 更该修的是「增量环节崩了不该丢整篇」

`repick_title` 只是**重拟一个标题**，属于增量；它崩掉却把整篇稿子丢了，
还连撞 3 次（3 次 LLM 调用全浪费）。现在包了 try/except：

```python
try:
    _new_title = repick_title(...)
except Exception as _e:
    traceback.print_exc()
    degrade.note("标题重拟异常", f"{type(_e).__name__}: {str(_e)[:60]}",
                 action="保留原标题继续成稿（只影响增量，不丢整篇）")
    _new_title = ""
```

口径一致：「只影响增量的缺失不丢整篇，保存侧兜底 + degrade 留痕」。

## 四、批次状态：失败的批次曾被标成「已完成」

发布步骤 exit 1 后，「回写批次状态（幂等保护）」仍然把 `evening` 写进
`batches_completed` → 批次显示已完成 → **人工补发会被幂等跳过，该批永久丢失**。

修法：给发布步骤加 `id: publish`，回写条件追加 `steps.publish.outcome == 'success'`。
本次已手工把 `evening` 从 `output/2026-11-05/metadata.json` 的
`batches_completed` 移除，否则补发连跑都跑不起来。

代价：真失败的批次会被 30/50 分兜底 cron 重试一次 —— 这比静默丢批好。

## 八、顺手补掉的观测缺口：v2 硬闸门不入台账

`verify_publish_gate` 里硬项「一致性校验拦截率可统计」（计划 7.3）当晚报红：

```json
{"events": 2, "blocking_checks": 0, "rejects": 0, "warn_only": 2, "reject_rate": null}
```

不是误报：v2 之后改写路径只在**被拦**时走 `_note_consistency_reject`，通过时一条不记，
分母恒为 0 → 拦截率永远「未接入」→ **硬项永久红**。而长期红灯本身就是漏洞
（它会把真回归变成「已知噪音」）。

修法：`gate_v2.attach` 之后无条件 `record(blocking=True, passed=not block, ...)`，
`blocking=True` 语义是「这是一道硬校验」（不等于它拦了）。埋点外包 try/except，
炸了只丢观测不阻断生成。新增 `tests/test_gate_v2_ledger.py` 3 项钉住：
通过也要留分母、被拦记分子且能算出 100%、台账写失败不得影响成稿。

副作用与修复：加了「通过也入账」后，任何跑到 `_rewrite_with_retry` 的用例都会写真实
`data/consistency_stats.json`（实测跑一次全量单测，真实台账混入 3 条假事件，
title 是某条用例的假稿）。已在 `tests/conftest.py` 加 autouse 夹具默认把台账指到
`tmp_path`，跑完全量单测复核台账仍为 **0 条**。
