日期：2026-11-09
对照材料：
- 选题漏斗：`topic_funnel.py`（8 层，11-04 建立，11-09 补了失败原因与落盘口径）
- 审核逻辑：`docs/audit/2026-11-06-审核逻辑精简-对齐头条发文规则.md`

## 结论

| 问题 | 结论 |
|---|---|
| 流程节点上冲突吗 | **不冲突**。两者串联在不同环上：漏斗管「选题→生成」，审核管「成稿→发布」 |
| 判断条件上冲突吗 | **不冲突**。两边零共享判据，不存在「同一件事判两遍」 |
| 有冗余/无效环节吗 | **有 3 处**，但都不是「整层冗余」，是层内三个具体点 |
| 建议删除吗 | **不删任何层、任何合规项**。3 处全部按「补实现 / 前移 / 换判据」处置，**一个字都没删** |
| 删了会怎样 | 删漏斗 → 回到「为什么今天只发 1 篇只能人肉读日志」；删合规项 → 直接对着一档扣分 |

## 一、两者不在同一环上：串联，不是并列

```
  素材 ──▸ 选题 ────────▸ 生成 ────────▸ 落盘 ──▸ 发布
              │                              │
              ▼                              ▼
    ┌─────────────────────┐      ┌──────────────────────┐
    │   选题漏斗（8 层）   │      │  头条审核（14 条规则）│
    │   只记录，不判定     │      │  判定扣分，命中丢该篇 │
    └─────────────────────┘      └──────────────────────┘

llm → dedup → material → category → batch_mix → slot → generated → final
                                                              │
                                                              ▼
                                                    save_articles_local
                                                    出口合规 → 丢弃该篇
```

`topic_funnel.py` 的文件头自己写死了这条边界：

> **它不是闸门**。本模块没有任何阈值、不做任何判定、不阻断任何流程，因此**不进 `pre-publish`**。
> 给它加阈值，它就变成第 43 项审核 —— 而这轮工作的主题恰恰是「审核太多、验证太少」。

代码核对过：`topic_funnel.py` 里唯一的 `raise` 是参数校验（层名非法、剩余数为负）
和 CLI 退出（`raise SystemExit(main())`），**没有一处能拦住发布流程**。

**所以「流程节点冲突」这个假设不成立。** 一个是仪表盘，一个是刹车，装在不同位置。

## 三、四处分工模糊：不是冲突，是「没人写清谁管哪一半」

### 3.1 时效：三处各判一段，其中一段是空的

`TT-03.why_keep` 声称有三道判据：

| 声称的判据 | 实际实现 | 位置 |
|---|---|---|
| ① 素材 pubDate ≤36h | ✅ 有 | `hot_sources` 时效闸门（生成前） |
| ② 成稿正文的绝对时间词与发布日冲突 | ❌ **不存在** | 全仓 grep 无实现 |
| ③ 赛程稿 `publish_by` 晚于当前 | ✅ 有 | `j_freshness` |

**②是空号。** 我用 `grep -rn "时间词|time_word|旧闻新发"` 扫过全仓（排除 tests），
只有 `extractor.py:58` 的一个抽取用词表，它不是判定。

这不是「删多了」，是**规则表承诺了一件代码没做的事**。属「有结论没证据」的反面：
**有要求没实现，而且覆盖校验抓不到**——`verify_rule_coverage` 的 B 项只验证
「规则表的 `judge` 名字在代码里有实现」，不验证 `why_keep` 里承诺的分项是否都在。

### 3.2 按类型删题：两个地方删，一个是增长、一个是合规

| 位置 | 删什么 | 依据 | 性质 |
|---|---|---|---|
| 漏斗 `category` 层（`topic_category.prioritize`） | 战报比分超单批软上限 | R11 阅读量诊断 | **增长**，可回滚 |
| 审核 `content_mix` 项（TT-03） | 历史回顾（`TARGET_PCT=0`） | 平台旧闻 70 分 | **合规**，硬拦 |

两者看起来都是「按类型删题」，但对象和依据都不同。**不能合并**——把合规项并进
增长项，等于让一个可回滚的运营策略去决定扣分风险。

### 3.3 防重复：三个粒度，各管各的

| 判据 | 粒度 | 防什么 | 位置 |
|---|---|---|---|
| `dedup` event_key | 选题 | 同一件事写两遍 | 漏斗第 2 层 |
| TT-06 `j_plagiarism` | 成稿 | 与源文实质性相同（洗稿） | 出口 |
| TT-14 `j_low_quality_aigc` | 批级 | 相邻篇模板化/句子重合 | 每日体检 |

三者互不覆盖：dedup 拦不住洗稿（措辞不同），TT-06 拦不住「同事件换三篇不同写法」，
TT-14 只在样本 ≥5 时才有意义。

**但 TT-14 是第三条「告警无消费者」**：11-06 文档已记 `P1-2`——去重的弱判据告警
没人消费，TT-14 又自己写了一套。到今天仍未接上。

### 3.4 事实：一个是预防，一个是核验

| 判据 | 时点 | 判什么 |
|---|---|---|
| 漏斗 `material`（`_check_topic_material_sufficiency`） | 选题 | 标题提到的队，**有没有**已完赛数据 |
| TT-02/05（`j_fact_conflict`） | 成稿 | 写出来的数据，**对不对** |

「有没有」和「对不对」是两件事，互补，不重叠。但 material 的实现方式有硬伤（见 4.3）。

## 四、真正的冗余 / 无效环节（三处，都有证据）

### 4.1 【真冗余】TT-03 的时效判据：两道判据**全都没有数据**

- **性质**：不是重复实现，是**承诺了没做**，而且比最初判断的更糟。
  `why_keep` 明写三道判据，代码只有两道；进一步查接线后，那两道也都是空转：

  | 判据 | 状态 |
  |---|---|
  | `publish_by`（确定性供给的发布窗口） | `fixture_library.py:416` 生成了，但**从未拷贝到成稿** —— 成稿字段白名单里没有它 |
  | `source_age_hours` | **全仓没有写入点**，只有 `verify_compliance.py` 在读 |
  | 「成稿正文绝对时间词」 | **不存在**，`grep 时间词` 只命中 `extractor.py:58` 的抽取词表 |

  所以 TT-03 在真实数据上**恒为「未判定」**——不是「少一道」，是三道全空。
- **影响**：发一篇把「今天」写成前天的稿子，这一项完全不设防，而报告上只显示
  「未判定」，看起来像环境问题。
- **处置（本轮已做）**：选「补实现」，不是删承诺。
  1. 补 `j_time_word` 判据（`scripts/verify_compliance.py`），规则表
     `judge: freshness + time_word`，两截判据按 `_merge` 合并（任一红即红）；
  2. 把 `publish_by` 接进成稿（两处白名单拷贝都漏了它），让第一截也有数据；
  3. `why_keep` 改成如实描述，并新增 `coverage_gap` 明写
     「素材时间戳未落库 → 旧闻搬运判不了」。
- **为什么不能只删那句承诺**：删了的确「不减少实际保护」，但也等于承认这项永久空转。
  平台对旧闻新发是按 70 分档扣的，而本账号历史上真犯过（2018 年新浪 RSS 当新闻源）。

### 4.2 【真浪费】历史回顾：选题层不拦，跑完整条生成链路才在出口丢

- `content_mix.TARGET_PCT["历史回顾"] = 0.0`（禁发）
- 但 `ZERO_TARGET` 在 `orchestrator.py` 里**没有任何调用点**，只在
  `scripts/verify_batch_mix.py:202`（验收脚本）里被读
- `topic_category.prioritize` 只删「战报比分超限」，不删历史回顾
- 唯一真正的拦截在 `reservoir.is_banned`（蓄水池出口）和 `verify_compliance` 的 `content_mix` 项

结果：一条「历史回顾」选题如果从 LLM 出来，会走完 dedup → material → category →
batch_mix → slot → **生成（花 LLM token + 配图）** → 出口被丢。

- **风险实际很低**：`prompts/topic_selector.txt` 的品类枚举里本来就没有「历史回顾」，
  LLM 不会主动输出。所以这是「结构性浪费」而不是「每天在烧钱」。
- **该怎么做**：**不要删出口那道**（防绕过），而是把判据**前移**到 `category` 层
  加一道（命中就丢题，不生成）。这是「前移」，不是「删除」。
- **本轮已前移**：`content_mix.is_banned()` 成为「禁发」的**唯一判据入口**
  （先 `normalize` 再查 `TARGET_PCT == 0`，避免 `榜单`/`战术解析` 这两个别名键
  被当成禁发），`orchestrator` 在 `category` 层调用它，漏斗 detail 记 `禁发=N`。
  出口那道**原样保留**。
- **能不能安全删出口那道**：**不能**。前移只挡计划内路径，出口是唯一兜住
  「新通道不知道这条规矩」的地方——11-06 已经因为漏装闸门吃过一次。

### 4.3 【判错，不是冗余】material 层用 `WIKI_TEAMS` 硬编码 15 支队当「已知队」基准

`orchestrator.py:845` 起，`material` 层把 `constants.WIKI_TEAMS`（15 支队）
当作「这是一支真实球队」的判据，再手写一张 `eng_names` 表补英文名。

**修正一句初判**：这条只错了**一个方向**，不是两个。表外球队带「进球/点球」的稿子
旧实现也拦得住（走的是 `else` 分支的 `has_match_details`）。真正错的是：

- **表内球队被过度丢弃**：只要今天没有它已完赛的比赛，「拜仁的中场结构该怎么改」
  这种**根本不需要比赛数据**的分析稿也被丢
- 错因不是「词表太短」，而是**拿球队白名单当素材判据** —— 补词表只会把同一个
  错误施加到更多球队上（这正是「硬编码词表是定时炸弹」那条事故的同型）

这条**不能删**（它防的是「没有数据也硬写 → 幻觉 → TT-02 谣言 70 分」），
但**判法必须换**：判据收敛成「① 今天有这队的已完赛数据 → 放行；
② 否则只要选题要素要比赛细节就丢，转会/八卦豁免」，且不再持有任何球队白名单；
「是否提到球队」改用 `data_chart.alive_owners`（扫全局 `entity_map`、最长匹配消解，
与配图相关性共用同一实现）。

**真实数据回放**：用 11-05~11-09 的 5 份 `metadata.json` 逐条跑新旧判据，
保留量 **9 → 13**（+4），同一天那条「要比赛数据但没数据」的稿子仍被拦。
这同时是 `batch_mix` 反复降级的一味供给药。

## 五、可删 / 必留清单

### 可以安全删除的：**0 项**（结论随落地过程改了）

初判时认为「`TT-03.why_keep` 里那句时间词承诺」可以删——它当时确实是假承诺。
但补实现时发现真实情况更糟：**三道判据全都没有数据源**（见 4.1 的表）。
这时删掉承诺等于把一项 70 分档的防线**永久注销**，所以选了补实现。

**最终处置：一个字都没删。** 三处都是「补实现 / 前移 / 换判据」。

### 必须保留（逐条给原因）

| 保留项 | 删了会怎样 |
|---|---|
| **漏斗全部 8 层** | 回到 11-04 之前：回答不了「这一篇被哪一层挡掉的」，S2 配额归并失去唯一数据源。它不判定、不阻断、成本是几十行 jsonl |
| `llm` / `dedup` / `material` / `category` 四层 | 这四层在 `select_topics` 内，删任一层就看不见候选在哪一步消失 |
| `batch_mix` / `slot` / `generated` / `final` 四层 | 这四层是 11-09 刚修好的口径（失败原因 + 落盘）。删了等于退回「成稿数虚高 2 篇」的旧账 |
| **10 项 compliance** | 每一项对着一档扣分（70/20/10/5）。删一项 = 主动放弃一块防线，且 `verify_rule_coverage` 的 D 项会立刻红 |
| `content_mix` 禁发类型 | 唯一「发出去撤不回来」的项（旧闻 70 分） |
| `image_relevance` | 平台明列「图文不符 10 分」，且是全仓唯一做到绘图侧与验收侧共用 `entity_hits` 的地方 |
| `rumor_wording` | 「传闻写成确定信息」同时命中谣言 70 与标题党 70，是**双罚点** |
| `dedup` 两道硬判据 | 删了会每天重写同一场比赛；但**弱判据告警**可以删（见下） |
| TT-14（warn） | 唯一覆盖「账号级处置」的项，没有分值所以最容易被当不紧急——但它对应的是封号，不是扣分 |

### 可以考虑删、但本轮不建议删的（有争议的 1 项）

| 项 | 支持删的理由 | 反对删的理由 | 建议 |
|---|---|---|---|
| `dedup` 的「关键词重叠」告警 | 无人消费，且 `TT-14` 又写了一套 | 删了就连「有没有人在意」都看不见了 | **先接消费者**（喂给 TT-14 或每日体检），再决定删不删。别直接删 |

## 六、结论性建议

### 不建议删除任何层、任何合规项

三条理由：

1. **删漏斗没有收益，只有损失。** 它不阻断、不判定、不花钱，唯一的成本是几十行 jsonl。
   删了立刻回到「为什么今天只发 1 篇，靠人肉读日志猜」的状态——这正是 11-04 建它要解决的问题。
2. **删合规项是拿扣分换清爽。** 每一条规则背后是一个具体分档（70/20/10）。「审核太复杂」
   的正确解法是 11-06 已经做过的那件事：**把非合规项移出「审核」这个筐**（39 项体检仍然跑，
   只是不再决定今天有没有稿子发）。而不是继续往下砍。
3. **两者本就不在一个环上。** 把仪表盘和刹车当成重复装置，是概念混淆。

### 真正该做的三件事（都不是「删除」）——**已全部落地，见第八节**

| 优先级 | 动作 | 类型 | 状态 |
|---|---|---|---|
| P0 | TT-03 的「时间词」判据：补实现 | 补 | ✅ 已补 `j_time_word` + 接通 `publish_by` |
| P1 | 「历史回顾」禁发判据前移到 `category` 层（**出口那道保留**） | 前移 | ✅ 已前移，`content_mix.is_banned` 为唯一判据 |
| P2 | `material` 层的 `WIKI_TEAMS` 换判据 | 换口径 | ✅ 已换成「要不要比赛数据」，不再持有球队白名单 |

### 如果坚持要「精简」，唯一站得住的理由是

> 「审核太复杂」的真实痛点不在**项数**，在**同一层里混着不同性质的东西**。

11-06 已经把 47 项按 scope 分成 6 类，把 pre-publish 从 10 项降到 6 项且全是 compliance。
**这一步做完之后，继续删就进入负收益区**——每删一项，失去的保护都是具体的、可命名的。

## 七、删除后可能带来的风险（如果一定要删）

| 删除对象 | 直接风险 | 多久会显现 |
|---|---|---|
| 漏斗任一中间层 | 损失无法归因到具体层，报告出现「无主损失」；S2 归并重新变成凭直觉 | 立刻（当天报告就说不清） |
| 漏斗整体 | 只能靠 `metadata.json` 反推，而它**只保留当天最后一批**的 `batch_mix`——13 个批次的降级会被看成 1 个 | 立刻 |
| `material` 层 | 无数据支撑的选题进入生成 → 幻觉 → 命中 TT-02 谣言 **70 分** | 1-3 批内 |
| `content_mix` 禁发 | 历史回顾这类「已被自己证明天花板为 0」的稿件重新发出去 | 蓄水池有 16 条存量，随时可发 |
| `image_relevance` | 图上印了正文没提的球队 → TT-09 **10 分** | 图源抖动时随机出现 |
| `rumor_wording` | 传闻写成官宣 → 同时命中 TT-02 与 TT-04，**双 70 分** | 转会窗高频 |
| TT-14 | 账号级处置（限流/禁言/封号）从「可见」变「不可见」 | 慢，但不可逆 |

## 九、两个遗留缺口：必须解决吗（2026-11-09 追加核查）

上一节把两个缺口都记成了「已如实登记、未解决」。追加核查后结论并不一样：
**一个是真缺陷且正在发生，必须修；另一个是比例型风险，不必修到零，但必须加阈值告警。**

### 9.1 更正上一节的一句话

上一节写「`verify_compliance` 本机 rc=2 是正文留在 runner 上，不是代码问题」——
**后半句是错的**。它不是「本机才有」，而是 **CI 上每天也在红**：

| 事实 | 证据 |
|---|---|
| 日报门禁自加入以来从未绿过 | `daily-result.yml` 的「合规审核」步骤加入于 `011d3b7`（2026-11-06 14:43）；此后 11-07 05:49Z、11-08 05:52Z 两次运行均 `failure`，失败步骤正是它，起止同一秒（秒退） |
| 失败码是 rc=2 而不是真违规 | 本地复现同一批数据：`verify_compliance --days 1` → `rc=2`，11 条 block 级规则里 8 条「未判定」 |
| 根因 | `.gitignore` 第 2 行只放行 `output/**/metadata.json`，成稿 `*.md` **从不入库**（`git ls-files output` 里 `.md` 计数为 0）。每日 job 是全新 checkout，正文读不到 → 正文级判据全部「未判定」 |

### 9.2 缺口一（`source_age_hours` / 时效证据）：不必修到零，但现在是「沉默的比例」

实测（`data/freshness_ledger.json`，近 5 天 74 批）：

| 指标 | 数值 |
|---|---|
| 检查素材 | 678 条 |
| **时间无法判定（被保守放行）** | **189 条 = 28%**，全部来自「热点媒体」 |
| 有时间的素材里被闸门剔除 | 51 条（51/489 = 10.4%） |

闸门本身是有效的（有时间就拦得住 10%），问题在**另外 28% 从未被时间检验**。
且没有任何阈值看着它——`verify_publish_gate` 的 E 项只判「已知超时仍被保留」，
`unknown` 只写进 detail 一行文字。**源站改版把时间字段弄丢，28% 会变成 100%，而报表不会红。**

实际暴露量（不夸大）：22 篇成稿里 4 篇来源是 `dongqiudi.com`，
按 28% 折算约 **每 5 天 1 篇稿子的素材时间不可核验**。命中即 TT-03（70 分档），
原文注释写的是「扣一次直接掉出分成门槛」。

**结论：不是「必须立刻修到 0」，但「现在这样连告警都没有」不可接受。**
两件事分档做：① 加 unknown 比例上限（低成本，必做）；② 把 unknown 降下来（改采集正则，可排期）。

### 9.3 缺口二（正文级判据在每日档天天未判定）：必须修，而且优先级高于缺口一

它同时犯两条项目纪律：**长期红灯本身就是漏洞**（红久了就没人看）、
**「未判定 ≠ 通过」被写进了文档却没人消费**。更实际的是：TT-01 赌博话术、
TT-07 诱导交互、TT-08 违规涨粉、TT-13 无资质专业内容这 4 条 70 分档规则，
在每日档上**从来没有真正判过一次**——真实违规不会被告警，只会显示「未判定」。

三种修法，只有一种是对的：

| 方案 | 评价 |
|---|---|
| 让 `output/**/*.md` 入库 | **否决**。仓库膨胀 + 正文版权/合规风险，且等于把成稿当源码管 |
| 每日 job 只判标题级，正文级标 `n/a` | **否决**。这是把「读不到」洗成「不适用」，正是 11-06 事故的镜像 |
| **生成 job 把逐篇合规结论落盘，每日 job 读结论不再重判** | **正解**。`batch.yml` 生成后、发布前已在同一 runner 上跑过 `--drop-violations`，`data/audit/compliance_dropped_*.json` 已在库；每日档只需核「这批有没有做过正文级审核、结论是什么」 |

### 9.4 顺带修掉的一个自身缺陷

上一节落地的 `time_word` 让 TT-03 变成两截判据，而计数仍是「按判据条数」，
于是报告印出「**4/2 篇**未判定」。自相矛盾的数字比没有数字更糟，已修：
新增 `_combine_same_article`（同一篇先合并、再跨篇计数），现为「2/2 篇未判定」，
并加 3 条单测锁住（其中一条是负向：摊平不聚合必须重新印出 4/2）。
