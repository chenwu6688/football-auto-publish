### 为什么合规判据没错

TT-07/TT-08 对应头条《信用分机制》两条 20 分档，判据匹配的是「引导语境」而非孤词
（`关注老六` / `点个关注` 都带动作）。**错的是生成侧**：自己在提示词里教模型写
被平台扣分的话术。这正是 11-06 那次事故的同形复发——当时修了提示词，但**只修了
被扫到的三处**，`brand_manual.yaml` 与 `refill_reservoir.py` 从没进过扫描面。

### 关键口径：删句修复的边界

`verify_compliance.repairable_by_sentence()` 从**规则表**读判据，不在调用侧列 ID 白名单：

- 只有 `judge == "inducement"` 且 `credit <= 20` 才允许删句；
- 不实信息 / 侵权 / 赌博（70 分档）**删句等于抹掉错误证据**，一律整篇丢；
- 删完必须重判，仍命中就按原判丢弃（删句是补救，不是豁免）；
- 删了哪几句落进 `metadata.compliance_sentence_removed`。

## 三、②的根因与修复（独立故障）

run 43033339536 的分步结论：`安装依赖` **failure**，其后 `写入登录态` / `回收后台导出`
全部 **skipped**。也就是说**脚本根本没跑**，失败通知里那句「脚本未产出状态文件
（可能在启动阶段就崩了，如依赖/登录态解压）」是**错的归因**——它把「没装好环境」
说成了「脚本崩了」，人照着这条文案只会去查登录态和页面改版。

- 现有证据只能定位到「安装依赖」这一步（`pip install` / `playwright install chromium`
  / `playwright install-deps` 三条命令塞在同一个步骤里），分不清是哪一条；
  同一天 18:00 的 batch.yml 用同样三条命令且成功 → 偏向瞬时网络/apt 抖动。
- 修复：三步拆成 `deps` / `browser` / `browser_deps`（各带 id），失败通知**先读步骤结论**
  再读脚本状态文件；兜底文案改成「回收脚本已运行但未落状态文件（不是安装/登录态问题）」。
- 下次失败会直接说清是哪一步，不必再猜。
