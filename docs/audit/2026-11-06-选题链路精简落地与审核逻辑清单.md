## 一、热点池：只加懂球帝 + 贴吧

### 1.1 一份协议，不在 `hot_topics` 里写 if-else

`hot_sources.PROVIDERS` 是唯一的源清单，每个源声明三件事：

| 字段 | 取值 | 决定什么 |
|---|---|---|
| `kind` | `board` / `media` / `ugc` | 能不能当**事实底本** |
| `tier` | P0 / P1 / P2 / P3 | 先接谁、能不能接 |
| `enabled` | bool | 关掉的必须写 `note` 说明原因 |

本轮的落地：

| 源 | kind | 状态 | 理由 |
|---|---|---|---|
| 懂球帝 | media | ✅ 启用 | 编辑部稿件，有正文可抓 → **可当事实底本**；11-06 实测首条就是「C罗自宣退出葡萄牙国家队」 |
| 百度贴吧 | ugc | ✅ 启用 | 话题榜 JSON 30 条，但足球只占 3/30 → **只能当热度信号**，绝不当底本 |
| 新浪体育 | media | ⛔ 关闭 | RSS pubDate 全是 2018-09（死档），接入即旧闻新发 |
| 腾讯体育 / 虎扑 / 球天下 / Goal / k7 | media | ⛔ 关闭 | 纯 JS 壳 / 全 JS 渲染 / Cloudflare / 需合规评审 / 查不到正规新闻站（博彩 SEO） |

### 1.2 媒体源必须过时效闸门（36h）

`hot_sources.apply_freshness` 只对 `kind="media"` 生效，**解析器复用 `utils.filter_fresh_news`**
（仓里已有一份，再写一份就是「同一量两处定义」）。两条边界：

- 榜单行不套时效：榜上没有发布时间，「此刻在榜」就是新鲜，套时间会把它整批判成未知；
- 媒体行拿不到时间 → 保留但标 `unknown`，并计入 `diag.unknown_time`（拿不到时间 ≠ 过期）。

`diag` 逐源记 `status/count/elapsed_s/stale_dropped/stale_samples`：台账里必须能分出
「今天没热点」与「源挂了」——这两种处置完全不同。

### 1.3 三通道合并与去重

`hot_topics.pick_candidates(board, media, news)` 按证据强弱排序：

1. `board` —— 榜上有名次，说明**大家真的在谈**（最强热度证据）；
2. `media` —— 编辑部头条，说明**有事实底本**（最强事实证据，境外 runner 榜单被墙时靠它）；
3. `news_cluster` —— 同题 ≥2 篇（降级通道）。

同一条事件在多源出现时只出一条候选，`providers` 记下上过哪些源：
`["dongqiudi","tieba","weibo"]` 本身就是最强的热度证据。

一条纪律没变：**没有事实底本不产出候选**。贴吧话题再热，也必须有报道配对才进候选。

## 二、槽位账修复（P0，本轮最实质的一处）

### 2.1 事故链

```
batch_mix.assign(topics, max_articles=2)     → 规划 main + data 两槽
确定性供给（赛程稿）在此之后生成，先占 1 槽
_main_slots = 2 - 1 = 1  →  topics[:1]       →  data 槽那条被静默丢弃
```

11-06 漏斗原文：`llm 4 → dedup 4 → material 4 → category 4 → batch_mix 2 → slot 1 → generated 1`。
metadata 里那句「data 槽无可用候选，本批少写 1 篇」**是不实记录**：候选有，是被顶掉的。

后果：`TARGET_PCT` 给数据对比 30 + 排行榜 18 = 48%，结构性不可达；实测数据型 9.1%、
战术榜单 36.4%（目标 4%，容差上限 14%）。

### 2.2 三处修法（缺一条就复发）

| 修法 | 实现 | 为什么必须这样 |
|---|---|---|
| 确定性供给只填空槽 | `collect_fixture_topics(need_type=...)`，填不上返回空 | 它 5 种角度里 4 种落「战术榜单」，硬塞就是每批 1 篇 4% 类型的稿 |
| 主稿跳过已填类型 | `_select_main_draft(topics, articles, main_slots)` | 不跳过就会「确定性写 data、主稿再写一遍 data」，两篇同型缺热点 |
| 类型名归一 | `content_mix.ALIASES["数据对照"] = "数据对比"` | 别名缺席时：配比统计永远 0%，且 `DAILY_CAP` 查不到 → **没有单日上限** |

顺带说明：`verify_batch_mix` 的「产出结构」判项原来拿 11-04 之后的批次判新规则，
而这批批次本身跑的是**有 bug 的槽位逻辑**（数据型 9.1%）。现改为从 `SLOT_SINCE=2026-11-07`
起算，旧样本如实计入 `legacy` 并打印 —— 不隐藏，也不让一条永远无法通过调度的红警常驻。

## 三、去重：5 道 → 2 道 + 1 道告警

| 旧（5 道，串在一个函数体里） | 新 |
|---|---|
| 批内关键词 ≥50% → 删 | **hard 1 同一场比赛**：对阵键（今日 `fixture_pairs`）+ 赛果指纹（7 天） |
| 跨批次标题/关键词 40%/对阵/指纹 | **hard 2 同一件事**：`event_key` = 实体 + 事件族（今日热点键 + 今日/7 天标题算出） |
| 昨日关键词 40% → 删 | **warn 关键词重叠**：只打印 + 记漏斗，**不删题** |
| 7 天事件指纹 → 删 | （并入 hard 1） |
| 7 天关键词 50% → 删 | （并入 warn） |

三点说明：

1. **弱判据不能当删题判据**。关键词是 LLM 自由生成的：换个说法就绕过，同队不同事就误杀。
   供给本来就窄，错杀的代价比漏放高。
2. **批内去重不再单独一道**：逐条判定时把已保留候选的键加进集合，第二条自然被挡住。
   旧的 `_check_intra_batch_dedup` 已删除 —— 留着就是两套实现（`verify` 里有断言防回归）。
3. **主稿通道现在也看事件键**。以前只有热点通道按 `event_key` 去重，主稿只看关键词与赛果指纹：
   同一条「C罗退役」上午热点写过、午间主稿换套关键词又写一遍，重叠率只有 20%，两道阈值都放过。

## 四、球员认知度兜底

`entity_map.json` 的 709 个实体里**没有 C罗、梅西、萨拉赫**（实测 `awareness_of('C罗') == '?'`），
而 `awareness_gate` 对未登记一律 `block`「未登记实体不得进入生成环节」。
→ 球员类选题在主通道上等于关闭，热点通道不得不绕过 ranker 才把 C 罗写出来。

修法：`awareness_gate.resolve_level(name)` 是唯一解析入口（实体表 → 球员译名表 → 未登记）。
已建译名的球员默认 **B**（关注者认识 → `needs_anchor` 放行 + 要求认知锚点）。

为什么不直接给 A：`player_names.json` 只解决译名，**没有分级依据**；A 是「泛球迷普遍认识」，
逐人断言需要证据。B 不拦截，只是要求配锚点 —— 保守但不会误杀。
实体表里已有的球员（姆巴佩 = A）保持原级，不被兜底降级。

## 六、审核逻辑的五个结构性问题

### 问题 1｜「静态判据」占大头（最值得改的一条）

不少验收项靠**读源码找字符串**：`"_hot_topic_cards(" in orch`、`"fixture_pairs" in fn`、
`"_check_intra_batch_dedup(" in src`。两类失效方向都实际发生过：

- **改个变量名就红**（`verify_hot_freshness` A 项曾按「定义点先后」判，永远误报）；
- **写个 if 分支就绕过**（把调用包进 `if False:` 依然能匹配到字符串）。

现有做法里已经有两种更好的范式，应该推广：
① `--selftest` 负向自检（改坏实现必须报红，`verify_hot_freshness` 已有）；
② 把逻辑抽成小函数直接单测（本轮 `_select_main_draft` / `dedup.apply` / `apply_freshness`）。

### 问题 2｜三态不统一

- 有的脚本 rc=2 表未判定，有的 rc=0 + `pending: true`；
- 有的 `ok: None`，有的 `skipped: true`，有的干脆不产出该判项。

于是「没有结果」有四种写法。CI 只看 exit code 时，**rc=0 + pending 会被读成通过**。

### 问题 3｜「未判定」在 CI 里等于绿

`for f in scripts/verify_*.py; do ... done` 只判 `$?`。rc=2（无 Key / 网络不通 / 无产物）
在流水线里与 rc=0 没有区别 —— 11-06 配图相关性事故就是「读不到证据」被当成「通过」的变种。
本轮 `verify_batch_mix` 的 pending 已经打印 `::warning::`，但**warning 不阻断**。

### 问题 4｜长期红灯（1 个）

`verify_title_anchor`：锚点覆盖率 33.3% < 40%。它红了很久，期间 `plan-invariants-verify`
后续 15 个 step 被连坐跳过（已加 `if: always()` 解开）。长期红灯本身就是漏洞：
它让真回归变成「已知噪音」。这一条需要改标题生成侧（三要素里的「专名/过程锚点」），
不在本轮范围，建议单开一轮。

### 问题 5｜阈值与目标仍有多处各写各的

`verify_batch_mix` 的三个目标已改为从 `content_mix.TARGET_PCT` 派生（好范式），
但 `DAILY_CAP` 与 `TARGET_PCT` 仍是两张表、`supply_mix` 的分层目标与计划 12.1 各写一份。
本轮已顺手修掉一处真实分叉（「数据对照」≠「数据对比」导致日上限失效），
同类问题建议一次性扫一遍：**凡是「同一个量」出现在两个文件里，都要选出唯一权威**。

## 七、建议同步调整（按性价比排序）

| 优先级 | 改什么 | 为什么现在改 | 怎么验 |
|---|---|---|---|
| ① | **统一三态**：`ok / fail / unknown(skip)` 三选一，落 `data/audit/*_latest.json` 统一字段；CI 汇总器对 `unknown` 发出 `::warning::` 并在周报里单列 | 问题 2+3 是「假绿」的根源，比多加判项有用得多 | 新增 `scripts/audit_summary.py` + 元验收断言「未判定不得记为通过」 |
| ② | **静态判据只保留「接线在位」类**，行为类一律改 `--selftest` 负向自检或抽函数单测 | 问题 1：改个变量名就红，写个 if 就绕过，两头都不准 | 逐脚本登记：每项的判法类型（static/behavioral/negative） |
| ③ | **扫「同一量两处定义」**：`DAILY_CAP` vs `TARGET_PCT`、`supply_mix` vs 计划 12.1 | 问题 5：11-04、11-05、11-06 三次事故同一根因 | 一张「量 → 唯一权威」对照表，验收脚本读表 |
| ④ | **修 `title_anchor`**：把锚点要求落到生成侧，或把阈值改成「生效日起」口径 | 问题 4：长期红灯让真回归变成噪音 | 红转绿，且不加 `continue-on-error` |
| ⑤ | **审核总数收缩**：402 项里合并同类（如 6 个标题脚本的「已接入生成侧」重复 6 次） | 47 个脚本一次全量跑近 2 分钟，且同一断言在多处重复 | 合并后判项数下降、覆盖率不降（逐项对照表） |
| ⑥ | 热点通道的真实效果看板：`hot_board_*.json` 里 candidates 命中率、`hot_event_key` 篇数、`providers` 分布 | 本轮把通道做通了，但「热不热」要数据说话 | `verify_hot_freshness` E 项由 0/38 转正 |
