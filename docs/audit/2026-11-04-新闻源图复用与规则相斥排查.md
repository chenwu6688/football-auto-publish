## 一、复用 `source_images`：可行性评估

### 1.1 数据流（这是评估的全部依据）

| 环节 | 位置 | 事实 |
|---|---|---|
| 抽取 | `media_scraper.py:1032-1043` | 战报正文 `<img>` → `report["images"]`，只要 `http(s)`，`width<100` 的当图标丢掉 |
| 落库 | `data_collector.py:392` | → `fixture["source_images"]`（懂球帝路径写死 `[]`，见 `:501`） |
| 旧消费者 | `orchestrator.py:2783` | `_find_source_article` → `source["fixture"]["source_images"]`，**唯一一条** |
| 上一版「修复」 | `_img_topic` | 读 `c["source_images"]` 与 `c["facts"]["source_images"]` |

**关键的坏消息**：字段真实长在 `c["fixture"]["source_images"]`，而上一版 `_img_topic` 找的是
`c["source_images"]` 和 `c["facts"]["source_images"]` —— **恰好漏掉了唯一真实存在的那一层**。
于是 6 处调用点全部「接线成功、数据为空」：函数在、调用在、单测绿、一张图也取不到。
这和 11-04 白天那个 `has_anchor` 被写成 `has_anchor()` 的坑是同一类：**静默失效**。

```
media_scraper ──images──► fixture["source_images"] ──┐
                                                     ├─► (旧) _find_source_article ✅ 1 条路径
                                                     └─► (旧) _img_topic          ❌ 找错了层，恒空
```

### 1.2 结论：可行，而且应当是第一优先级

| 维度 | 新闻源正文图 | 图库（Pixabay / Pexels / Unsplash） |
|---|---|---|
| 网络 | **0 次请求**（采集时已拿到） | 每篇 1~3 次 |
| Key | 不需要 | 需要；Unsplash 应用仍在人工审核（`api.unsplash.com` 401） |
| 图文一致 | **100%**（就是那场比赛的现场图） | 靠 query 猜，实测常配成别的场次/别的球员 |
| 版权 | 转述性引用，与「随便找张足球图」性质不同 | 各自许可条款 |

所以「不走图层方案」这个判断是对的——**最好的图源一直在代码里，只是没被消费**。

### 1.3 落地（三步，都不改采集口径）

1. **`source_images.py`（新增）** —— 把四个历史字段名收口到一处：
   `source_images` / `fixture.source_images` / `images`（media_scraper 原始）/ `facts.source_images`；
   过滤非 `http(s)`、`data:`、`loading./placeholder/icon/avatar` 占位图（不滤就会被下游静默跳过，
   又是「抓了等于没抓」）。
2. **`_img_topic(topic, *cands, match_data=None)` 两步取图**：
   - ① **直接取**：候选对象（fixture / source 结构 / facts）自己带图；
   - ② **关联取**：事件稿/赛程稿/预测稿手里只有选题、没有图，但说的就是本批抓过的某场比赛，
     于是按**队名二元组**去 `match_data` 里找回那场的战报图。
     **两支队缺一不可** —— 只命中一支就会把同城对手的图配上来，配错图是事实错误，
     无图只是缺图（有 `cover_card` 兜底）。同城两队别名重叠时直接跳过。
3. **接线补全**：`_add_event_result_articles` / `_add_event_angle_articles` 增加 `match_data` 形参，
   由 `main` 传入；`main` 的 4 处调用点、Pipeline A 改写路径、**紧急球评**路径全部改走 `_img_topic`。
   现在 **8/8 处 `search_images` 都由 `_img_topic` 供料**（此前是 7/8，紧急球评那条自己拼 topic）。

### 1.4 明确的边界（不吹）

- 懂球帝路径的 `source_images` 固定为空 → 命中率取决于当天有没有抓到直播吧战报；
- 标题只写一支球队的稿子**拿不到图**（故意的，见上）；
- **未验证**：真实批次的命中率。本地没有 `match_data` 快照，要等 11-05 之后的批次，
  看 `data/audit/scraper_fetch_*.json` 里 `news_source` 这条诊断记录。

## 二、规则相斥排查（5 处）

判据：**同一个量在两处各有定义、且两者不能同时满足**。这类问题不会报错，只会让告警永远亮着。

| # | 相斥的两处 | 实际表现 | 处置 |
|---|---|---|---|
| 1 | `batch_mix` data 槽**固定先取数据对比** vs `content_mix.TARGET_PCT` 给排行榜留 15% | 排行榜结构上**永远拿不到槽位**，占比恒 0%，每天必出一条「偏差 -15pp」 | 槽位内改按**目标缺口**选型（`_progress`），稳态收敛 25:15 ≈ 5:3 |
| 2 | `verify_batch_mix` 战术榜单上限 **25%** vs `content_mix` 目标 **10%** | 同一个量两把尺子差 15pp，按哪把都能说合格 | 上限/下限改由 `TARGET_PCT ± TOL_PCT` **派生**，不再手写第三套数字 |
| 3 | `verify_publish_gate` 同文件 A2 用 **0.90**、A5 用 **0.50**；且三要素是**硬闸门** | 一条硬闸门配「一半违规也算达标」的阈值 = 书面承认闸门可以不做 | A5 按生效日分口径：存量只留证、生效日后 ≥85%、样本 <5 判 ⏸ |
| 4 | `supply_mix` 清单自相矛盾：`战术榜单` 在 `_SOFT_SECTIONS`（按栏目名）却不在类型表；`紧急球评/战术解析` 未做别名归一 | 生成侧最常产的类型一旦缺显式标签 → 「未分层」→ **硬失败**，红的是验收不是标签 | 补 `_SOFT_BY_CONTENT_TYPE` + `classify` 先归一，并加「生成侧类型永不未分层」用例 |
| 5 | 计划 12.1 三级·软性 **20%** vs P1-1 每批结构必然推到 **~48%** | 两个数字**不可能同时满足**，告警永久亮 | **不软化阈值**（用户 11-04 的决定），改为在报告里拆「数据型 / 其他」两笔 |

第 5 处的拆解示例（真实窗口）：

```
三级·软性 19 篇拆解：数据型 8 篇（结构要求，计划 12.1 未计入的三级来源）/ 其他 11 篇（应压缩）
```

这样「三级 27.9%」这个数字就能一眼判断是**结构要求**还是**旧病复发**，
而不是每次都得回到代码里重新推一遍。

### 2.1 配比目标为什么改成 45/30/18/4/1/1/1

上一版是「按篇均阅读排序」定的（40/25/15/10/4/3/3），没人拿它跟结构对过。对一遍就露馅：

```
结构隐含（3 批/天 × 2 篇，候选充足）：热点 50.0% / 数据对比 33.3% / 排行榜 16.7%
旧目标：                            热点 40.0% / 数据对比 25.0% / 排行榜 15.0%  → 每天都「超标 10pp」
战术榜单：旧目标 10%（每天该有 0.6 篇），而结构上它只做补位 → 目标不可达
```

新数值 = 结构可产出份额 ± 补位余量，排序（热点 > 数据 > 排行 > 战术 > 低效）**完全保留**，
「压战术榜单、抬数据型」的原意没变，变的只是把数字改成结构真能产出的量。
`verify_batch_mix` 新增硬项把这条约束**机器化**：改 `STRUCTURE`/`SLOT_TYPES`/`_progress`/`TARGET_PCT`
任一处而不同步另一处，必红。

## 五、建议

1. **配图时效分层**：战报图是「这场比赛」的现场图，用在结果稿/隔夜战报/赛程稿最贴；
   跨天的事件稿、预测稿建议只在同一天用，否则读者看到旧图会当成新赛况。
2. **同批错开**：`event_cluster` 已有「同事件多切口首图必须错开」，源图复用后这条更容易触发
   （同一场比赛的图就那几张），建议把「同批同一 source_url 的稿件数 ≤2」也纳入观测。
3. **把「同一量两处定义」变成常态体检**：这轮 5 处相斥全靠人工对表发现的。
   现有 `verify_audit_health` 管「清单完整性/负向债务/硬项接线」，可以再加一类
   **口径重复登记**（同一阈值被两个脚本各自写死就报警）。这是下一步最值的自动化。
4. **`news_source` 命中率要进周报**：否则「复用图源」又会变成一条没人验证的改进
   （和 37% 无封面黑了很久是同一个教训）。
5. 用户侧仍是那三件：**头条号登录状态**、把 `PIXABAY_KEY/PEXELS_KEY/UNSPLASH_ACCESS_KEY`
   加进 GitHub Secrets、Unsplash 应用等审核。
