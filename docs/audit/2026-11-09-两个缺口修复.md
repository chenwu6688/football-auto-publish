## 一、缺口二：`daily-result.yml` 合规步骤自加入起从未绿过

### 现象

`daily-result.yml` 的「合规审核（头条扣分风险 · 唯一合规入口）」自 2026-11-06 加入，
每天都以 `rc=2` 收场。11-09 本地复跑（`--days 1`）：

```
⚠️ 过半 block 级规则未判定，本次**不能**视为合规通过（rc=2）。常见原因：正文留在了生成它的 runner 上。
block 级规则判定 1/12 条 / 未判定 12 条
```

### 根因

**不是判据坏了，是找错了证据。**

- 成稿 `output/<date>/article-*.md` 在 `.gitignore` 里（**故意的**——要发到头条的正文不该公开进 public 仓库）。
- 每日 job 全新 checkout，正文根本不存在 → 每条规则都落成「正文不可读」。
- 而 `verify_compliance` 的合同是「读不到证据判未判定」，于是 12 条 block 级里 11 条未判定 → 恒 `rc=2`。

> 这条纪律本身没错。错的是**它去现判**：出口审核（`audit_article`）在生成 job 里
> 已经拿正文逐篇判过一次，结论落在 `metadata.articles[*]._compliance` —— 而
> `metadata.json` 是 `git add -f` 入库的。同一批稿、同一份判据实现，结论早就在
> 仓库里，每天却重新判一遍并把结论覆盖成「不可读」。

实测覆盖（本地 `output/` 952 篇成稿）：

| 日期 | 成稿数 | 带 `_compliance` |
|---|---|---|
| 11-06 及之前 | — | **0**（出口逐篇审核未上线） |
| 11-07 | 4 | 4 |
| 11-08 | 5 | 5 |
| 11-09 | 2 | 2 |

**从 11-07 起每篇都有**。这份证据是可用的。

### 修法

`scripts/verify_compliance.py` 新增 `--from-ledger` 模式 + `recorded_verdict()`：

1. **只搬运、不重写**：回放的 status/detail 就是 `audit_article` 当时那条，逐字保留。
2. **缺结论 ≠ 通过**：metadata 里查不到该规则的结论 → 未判定，**绝不退回去现判**
   （现判在「读得到正文」的机器上会给出另一个答案 → 两台机器两种结论）。
3. **拒收非法 status**：落了不认识的 status 判未判定，不静默当通过。
4. **串行判据的坑**：只对「全部判据都是单篇级」的规则回放。混了批量判据的规则
   （`low_quality_aigc` 要 ≥5 篇正文）若一半回放一半现判，现判那半恒 UNJ，
   `_merge` 会把整条规则拖成**永 UNJ** —— 又造一个长期红灯。这类规则照旧现判。
5. **产物不共用**：daily 写 `compliance_ledger_latest.json`，batch 写
   `compliance_latest.json`。共用的话后跑的覆盖先跑的，`latest` 的含义每天在变。
6. **退出码三态不变**：`1`=有违规 / `2`=未判定 / `3`=全丢。`rc=2` 在新模式下的
   含义变成「**落盘结论覆盖不足**」，不是「源码坏了」。

顺带把退出码内联逻辑抽成 `exit_code(report, all_dropped, fail_on_block_only)` ——
让「终态判定」本身可被单测盯住，而不是只埋在 `main()` 里。

`daily-result.yml` 改为 `--days 1 --from-ledger --quiet`，**仍然不加
`--fail-on-block-only`**：`rc=2`（落盘覆盖不足）必须暴露。

### 验收

```
$ PYTHONPATH=. python3 scripts/verify_compliance.py --days 1 --from-ledger
合规审核（近 1 天 · 2 篇 · 规则表 2026-11-06 起 · 出口审核落盘结论回放）
  落盘覆盖：2/2 篇带出口审核结论
  ...
✅ 无 block 级违规（block 级规则判定 7/12 条 / 未判定 5 条 / 不适用 1 条）
RC=0
```

同一份数据，改前 `rc=2`（判定 1/12），改后 `rc=0`（判定 7/12）。

## 二、缺口一：时效闸门 28% 的「比例型盲区」

### 现象

`data/freshness_ledger.json` 近 5 天 678 条素材里 **189 条（28%）时间无法判定、
被闸门保守放行**，全部来自「热点媒体」。有时间的 489 条里拦掉 51 条（10.4%）。

### 风险形态

`verify_publish_gate` 的 E 项只查 `over_limit`（已知时效超上限仍被保留）——
那恰好是闸门**唯一看得见**的部分。真正的盲区是 `unknown`。

**源站改版把发布时间字段弄丢 → `unknown` 从 28% 一路涨到 100%，而 `over_limit`
始终为空、E 项始终绿。** 闸门彻底失效却无人知晓。

### 修法

E 项加 unknown 比例判定，阈值放在模块常量：

| 常量 | 值 | 依据 |
|---|---|---|
| `MAX_UNKNOWN_RATIO` | **0.50**（硬线） | 全仓对「未判定」的一贯口径就是「过半即不能算通过」（`verify_compliance` 的 `len(judged) * 2 < len(block_rules)` 即 50%）。**同一量两处定义不同阈值，就是 11-04「规则相斥」事故的起手式。** |
| `WARN_UNKNOWN_RATIO` | 0.35（告警） | 实测 27~28%，留 7 个点余量，日常不吵 |
| `MIN_UNKNOWN_SAMPLE` | 100 | 分母太小比例没意义 → 未判定，**不给 0**（否则「一次都没检查」看起来像满分） |

优先级：**已知违规 (`over_limit`) 最高**（铁证，不必等样本够）→ 比例超 50% 判红
→ 样本不足判未判定 → 越过 35% 判绿但写明告警 → 否则绿。

同时把 `runs == 0` 分支的返回结构补齐（加 `unknown_ratio: None` / `violation_records: []`）：
靠「键不存在」表达状态，下游只能猜。

### 验收

```
## 连续14天无旧闻新发（硬项）：✅
- 近 14 天闸门运行 82 次，覆盖 4/14 天；剔除超时效 52 条，未知 204 条（占已检查 749 条的 27.2%）
- 台账尚未满 14 天（累计 4 天，持续累积中）
- 无「已知时效>上限仍保留」✅
- 时间未知占 27.2%，在告警线 35% 内 ✅
```

## 三、修的过程中又发现一个：每日层看的是「今天」，不是「昨天」

> 这一条在第一次交付时**漏了**。用户追问「全部修复完了？」才回头核时序。

### 事故形态

`daily-result.yml` 名为「每日结果门禁（L3 · **看昨天真的发生了什么**）」，
但代码一直是 `--days 1`，而 `iter_items` 的窗口是 `today - timedelta(days=i)`，
`i` 从 0 起 —— **取的是今天**。

实测时序：

| 谁 | cron (UTC) | 实际 (CST) |
|---|---|---|
| `daily-result.yml` | `10 0` | 08:10 |
| 早批写完当天 `metadata.json` | `30 0`（主调度更早） | **08:05** |

**只差 5 分钟。** 早批一延迟（GitHub 排队 / 主调度 Cloudflare 抖动 / 兜底 cron 漂移），
08:10 时当天目录还不存在 → `articles=0` → `rc=2`。

这不是「合规不通过」，是**看错了日期**。而且它解释了为什么「换对证据」之后
这一步仍会**间歇性**红 —— 上一轮我在 15:00 本地跑出 `rc=0`，那不代表 08:10 的 CI。

### 为什么第一次没发现

`rc=2` 一直是同一个码。前三天根因是「正文不可读」（恒红），掩盖了「日期为空」
（间歇红）。修掉前者之后，后者才会浮出来 —— **同一退出码底下的两个不同故障，
必须分开验，否则修完一个就以为修完了。**

### 修法

`iter_items` / `verify` / CLI 加 `offset`：

- `offset=0`（默认）：从今天起算 → 本机、批次内、`--drop-violations` 用
- `offset=1`：从昨天起算 → **每日层**

daily 用 `--days 2 --offset 1 --from-ledger`：
昨天 + 前天（不是只取昨天，理由见下），并且报告里新增 `dates` 字段列出
「覆盖了哪几天、每天几篇」—— 只有总数的话，「9 篇」到底是昨天的 9 篇
还是跨两天各几篇，读的人无从判断。

### 为什么是 2 天窗口而不是 1 天

单日窗口会把「昨天恰好空批」变成假红；而「0 篇」本来就由发布成功率那项负责报，
不该让合规项替它报警。取 2 天与其它窗口式门禁（发布成功率 7 天、封面覆盖率 14 天）
口径一致。**FAIL 优先**，所以合并两天不会掩盖违规。

`batch.yml` 的 `--days 1 --drop-violations` **不改**：它要在批次内现判并移动当天
成稿，必须看今天，offset=0 正是对的。

### 验收

```
$ python3 scripts/verify_compliance.py --days 2 --offset 1 --from-ledger
合规审核（近 2 天（自 T-1） · 9 篇 · 规则表 2026-11-06 起 · 出口审核落盘结论回放）
  覆盖：2026-11-07×4、2026-11-08×5
  落盘覆盖：9/9 篇带出口审核结论
  ...
✅ 无 block 级违规（block 级规则判定 7/12 条 / 未判定 5 条 / 不适用 1 条）
RC=0
```

## 四、新增测试（43 项）

`tests/test_compliance_ledger_replay.py`（32 项）：
- `recorded_verdict` 六种输入（正常 / 缺规则 / 无字段 / 非 dict / 非法 status / 空 detail）
- 回放不改判（FULL_PASS → 无 blocking）、录得 FAIL → 必红

- 产物路径分离
- **窗口 offset 六项**：offset=0 起今天 / offset=1 起昨天且**跳过今天** /
  两天窗口 / 今天为空时不污染窗口 / `verify` 报出 `dates` 与 `offset` /
  **复现事故形态**（今天无产物 → 空窗口 → rc=2）
- workflow 接线六项（`--from-ledger` 必在、`--fail-on-block-only` 必不在、
