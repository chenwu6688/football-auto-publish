# 「本批无可发布文章」是什么状态 · 预测稿该不该永远不发 · 重拟链还剩哪些隐患

日期：2026-11-05 夜｜对应计划：7.3（闸门分级）/ 12.1（配额）/ 13.x（预测）
触发：用户三问 —— ① 这种状态怎么会出现；② 预测稿永远不发头条值得商榷；③ `score_title_plan` /
`title_elements.check` 没有 try/except 的隐患是什么、有何威胁。

---

## 一、`本批无可发布文章` 不是异常态，但现在被当成异常处理

### 1.1 它确实会出现，而且是结构性的

`publisher.load_articles` 命中「0 篇可发」有四条独立入口：

| # | 触发条件 | 真实成因 | 这次是否发生 |
|---|---|---|---|
| A | 日期目录不存在（也试了昨天） | 上游一篇都没产出 | — |
| B | 目录里 0 个 `article-*.md` | 同上 | — |
| C | 本批 0 篇，但目录里有别批的稿 | 本批生成全失败 | **是（11-05 18:00）** |
| D | 本批有稿，全被规则跳过 | 预测稿 / 禁发类型 | **是（11-05 19:25）** |

C 和 D 都是**真实存在**的状态，不是"理论上"。11-05 那天两种各撞了一次：

- 18:00：3 篇里 2 篇崩在标题重拟、1 篇是预测稿 → C+D 同时成立；
- 19:25：同形态再来一次，发布步骤 0 秒 exit 1。

### 1.2 真正的问题是**四种终态共用一个退出码**

```
有稿发出去了        → exit 1（当时也是 1！因为 publish_all 一律 return）
没有可发稿          → exit 1
上游空转            → exit 1
浏览器崩了          → exit 1
```

而 `batch.yml` 的「回写批次状态」当时只看步骤成不成功，于是**失败的批次被写成已完成**
→ 人工补发被幂等保护直接跳过 → 当批永久丢失（当晚就是这样，最后手工从
`output/2026-11-05/metadata.json` 移除 `evening` 才救回来）。

**同一件事：告警响了（红叉 + 手机推送），但恢复路径被自己堵死了。**

### 1.3 修法：三态退出码 + 台账留证 + 工作流分流

`publisher.py` 顶部新增契约（`EXIT_OK/EXIT_FAIL/EXIT_NOTHING_SKIPPED/EXIT_NOTHING_EMPTY`）：

| 退出码 | 含义 | 上层动作 |
|---|---|---|
| 0 | 至少一篇发出去了 | 正常收尾 |
| **2** | 本批**有**稿但全被规则跳过（`all_skipped`） | 标完成（重跑结果一样）+ warning |
| **3** | 本批**一篇成稿都没有**（`empty`） | **不**标完成，留给 30/50 分兜底 cron 重跑 |
| 1 | 真失败（登录失效/熔断/浏览器异常/全部发布失败） | 告警 + 人工 |

为什么 2 和 3 要分开：`all_skipped` 重跑一百次也是同一批稿子被同一条规则挡住，
重试只会把告警刷屏；`empty` 是上游空转（供给断了/额度耗尽/生成步骤静默失败），
**重跑有机会补上**。混成一个码，就只能二选一，要么丢批、要么刷屏。

配套三件事：

1. `load_articles` 不再自己 `sys.exit`，改抛 `NoPublishableBatch(code, detail, skipped)`。
   判据是 AST（`scripts/verify_publish_states.py` 判据 B）：**库函数不得自行终止进程**，
   否则调用方只能看到「进程没了」，没法翻译成「本批无事可做」，更没法落台账。
2. 无稿也落台账：`publish_ledger_{date}_{batch}.json` 增加 `counts.no_publishable`
   与 `no_publishable: {code, detail}`，当天聚合文件同步带上（`_merge_day`）。
   **不写台账的「0 篇」等于没发生** —— 10 月 62% 的漏斗缺口就是这么攒出来的。
3. `batch.yml` 发布步骤改成 `case "$RC"`：rc=2 收成功 + `::warning::` + Job Summary；
   rc=3 `exit 1` + `::error::`。回写步骤靠 `steps.publish.outcome == 'success'` 自动跟随
   （2 成功→标完成，3 失败→不标）。

### 1.4 顺手拆掉一颗更危险的雷：降级发布

原代码：批次筛选 0 命中且有文章时，**降级发布全部文章**（注释写的是"避免整批失败丢失内容"）。
真实后果是：晚上 0 篇 → 把早上已发过的两篇再发一遍 → 同一标题拿到第二个作品 ID，
而且它会"看起来很成功"（`发布 2/2 篇`），没有任何告警。

两处收口：

- 只降级**无批次归属**的稿（`batch_name` 为空，应急/补录稿才可能是本批的）；
  明确写了别的批次的一律不碰。
- 加一道保险丝：`_published_titles(date)` 读当天发布台账，已 `published` 的标题
  一律不再发（`status: skipped_already_published`，进 `counts`）。
  依据用台账而不是 `metadata.json.platform_id`：后者在 CI 里至今全是空
  （runner.temp 与仓库提交的不是同一份），拿它去重等于没有依据。

## 二、预测稿「永远不发」这条规则错在哪，怎么改

### 2.1 它是"用体裁替代质量判据"

R13 决策④ 的原意是「别拿无据断言冒充内容」。但实现写成了
`is_prediction == true → 一律不发`。于是：

- **该拦的**（无据断言、押比分）拦住了；
- **不该拦的**（有据前瞻：积分/战绩/净胜球摆在前面，结论跟着数据走）也一起拦了；
- 而且**没人能从日志里看出区别**——`reason` 只有"预测稿不发布到头条"五个字。

更要命的是这条规则**制造了第一节的 0 篇状态**：晚间批次唯一活下来的往往就是预测稿。

### 2.2 但也不能简单放开：现在的预测稿确实没有事实

`collect_future_matches` 只返回对阵名单（league / home / away / utc）。
`generate_prediction_article` 的 prompt 于是只能写「从近期表现来看」——那是模型知识，
不是我们核对过的事实。而且 `check_consistency_plan(..., blocking=False)` 对前瞻本来就是
warn-only，等于**没有一道闸门在核它**。

所以"拦"在现状下是对的，错的是**拦的理由**（按体裁拦）与**代价**（生成注定不发的稿）。

### 2.3 改法：先补事实，再按依据分级（`prediction_gate.py`）

生成侧（`orchestrator`）：

- 新增 `_prediction_basis(match_data, future_matches)`：把积分榜
  （排名/积分/净胜球/已赛场次）按**联赛 + 中文队名精确匹配**配到明日赛程上，
  英文队名经 `config/entity_map.json` 的 `name_en` 精确对译（不做模糊/包含匹配——
  "Manchester City" 与 "Manchester United" 互相包含，模糊匹配会把对手事实安到主队头上，
  那比没有事实更糟）。
- 事实注入 prompt：只许引用给定数字，写明"上面没有的比赛不要写任何数据"。
- **依据不足就不生成**：`_pbasis_n < 2` 直接跳过并打日志。
  以前是「先生成、再被 publisher 丢掉」，每天白烧一次正文调用。

发布侧（`publisher` → `prediction_gate.assess`）：

| tier | 判据 | 发 |
|---|---|---|
| `not_prediction` | 非预测稿 | 发 |
| `sourced_forward` | basis ≥ 2 项 且 标题无断言词 且 不押具体比分 | 发（批内 ≤1） |
| `opinion_only` | basis < 2（只有对阵名单） | 不发，理由写"依据不足 x/2 项" |
| `assertive` | 标题含「必赢/稳了/精准预测/稳胆…」 | 不发，理由列出命中词 |
| `score_guess` | 押具体比分（"我看好 2-0"） | 不发，理由带比分 |

两条判据细节值得写下来，因为都是踩过的坑：

- **断言词只查标题**（正文里的"血洗"常用于回顾上一场，查正文会误杀）；
- **押比分只认前瞻性触发词**（预测/看好/押/估计/会是/我觉得）。第一版把「打成/比分」也收进去，
  结果「上回合两队打成 2-0」这种**可核对事实**被判成押注 —— 自检里专门有一条钉这个区分。

### 2.4 口径必须同时改，否则「今天发了几篇」会各说各话

`build_metrics_dashboard` / `verify_batch_quota` / `verify_supply_mix` / `check_perf_lag`
四处各写了一遍 `not a.get("is_prediction")`（同一规则写四遍）。预测稿一旦能发，
这四处不改就会少算一篇发布量。收敛成唯一函数：

```python
prediction_gate.counts_as_content(article, pred_titles)
# 有成稿级 is_prediction 键 → 按依据分级判
# 历史数据没有该键 → 退回选题级 _is_prediction 按标题对拍（唯一证据）
```

## 三、重拟链剩下的两处裸调：隐患、威胁、修法

### 3.1 隐患是什么

`_rewrite_with_retry` 里标题处理是「评分 → 不过就重拟 → 再评分 → 三要素兜底」。
11-05 当天只给 `repick_title` 包了 try/except，**评分器与三要素判定本身还是裸的**：

```python
_sc, _sc_pass, _sc_reasons = score_title_plan(...)      # 裸
...
_sc, _sc_pass, _sc_reasons = score_title_plan(...)      # 裸，就在重拟后 6 行
if not title_elements.check(...)["ok"]:                 # 裸
    _fb = [c for c in title_brief.candidates(topic) ...]# 裸
```

同一形态还有三处副本：紧急球评、赛前预测、蓄水池准入（`_reservoir_accept`）。
而 `ensure_fixture_title` 更关键——确定性供给/战报/结果稿/多切口**四条线都从它过**。

### 3.2 威胁是什么（为什么这比"少一篇"严重）

1. **成本倒挂**：正文已经生成成功（最贵的环节、已烧掉额度），崩在最便宜的标题评分上，
   整篇丢弃。11-05 晚间 3 篇丢 2 篇就是这么来的。
2. **按重试次数放大**：这些代码在 `for attempt in range(max_retries)` 里，
   一次类型错会被放大成 N 次崩溃 + N 次 LLM 调用。
3. **advisory 项被异常升级成 hard 阻断**：v2 已经把标题评分降级为**只记分**，
   它的崩溃却在事实上决定了"这篇稿子发不发"。这与分级设计直接相反——
   等于让我们自己的 bug 决定今天有没有内容。
4. **"修了一半"最危险**：下一次崩在重拟之后的第二次评分，失败形态与那天完全相同，
   但 `degrade` 名字变了，排查要从零开始（还会被误读成"修了没用"）。

### 3.3 修法：一个安全入口 + 「未判定」语义

| 入口 | 行为 |
|---|---|
| `_safe_title_score(...)` | 返回 `(score, passed, reasons, judged)`；异常时 `passed=True, judged=False` |
| `_safe_elements_ok(title)` | 返回 `(ok, judged)`；异常时 `ok=True, judged=False` |
| `_safe_title_candidates(topic)` | 异常返回 `[]`（退回原标题） |
| `_unjudged(exc, stage)` | 统一留痕：print 栈 + `degrade.note` |

`ensure_fixture_title` 用项目已有约定 `-1 = 未判定`，四个调用方统一改成
`if s_score != -1 and s_score < 60:`。**不用 0 冒充**：0 是"判定为不合格"，
-1 是"没判定出来"，两者含义相反。

`judged=False` 会写进 `_title_score`，所以"今天有几篇没判定出来"是查得到的
——未判定 ≠ 通过，只是不阻断。

## 五、仍然存在的风险（这次没动）

1. **`sourced_forward` 依赖积分榜覆盖**：`standings` 只覆盖 football-data 的国内联赛
   （COMPETITION_IDS 里排除 UCL）。欧冠/中超/杯赛的对阵拿不到 basis → 归 `opinion_only`
   不发。这是有意的保守选择，但意味着"有据前瞻"目前只可能出现在五大联赛场次。
2. **断言词表是白名单式枚举**：新话术（"锁死""吃定"）不会被识别。判据只能收紧，
   放宽要靠回测——不要凭感觉往表里加词。
3. **`all_skipped` 不做重试**：若某天规则系统性误判（例如词汇表把正常稿判成违规），
   结果是"当天少一篇且不重试"。所以它必须配告警（已加 `::warning::` + Summary），
   但不能自动恢复。
4. **`publisher` 仍不校验平台侧是否已有同标题文章**：去重依据是我们自己的台账，
   台账丢了就失去依据（这也是 `data/audit` 绝不能进 `.gitignore` 的原因之一）。
