## 1. 改动点 1：补位层也过同一道去重判据

### 改了什么

去重此前只有**一层**：候选表层的 `dedup.apply`。补位层（`deterministic_supply.fill_gap` / `reservoir.fill_gap`）有自己的取货逻辑，**根本不经过这道判据** —— 同一场比赛换一行赛程就能再补一篇。实测 14 天「曼联 × 11 篇」。

- `dedup.exclusion_ctx(date_str, extra_titles, lookback_days)`：只**整理上下文**（跨批已覆盖 + 近 7 天历史 + 本批内存稿），不另行判定；
- `dedup.remember(ctx, title)`：补位逐条取货时把已定稿标题累加进上下文；
- `deterministic_supply.fill_gap(..., exclude=, stats=)`：`exclude` 收 dict（ctx）或 callable，**判据一律走 `dedup.judge`**，判据本身不复制第二份；命中者**不标记 used**（不悄悄消耗库存）；异常按不放行（fail-closed）；
- `orchestrator`：确定性补位调用点传入 ctx + stats；`_reservoir_accept` 末尾追加 `dedup.judge` 并把「标题不过」从 fallthrough 改成 `return`；漏斗 `final` 层新增 `补位拒绝重复` 计数（**只加在 final 层**——`_fill_reject` 定义在 6346 行，而 slot 埋点在 6532 行之前，加到 slot 层会 `UnboundLocalError`，当时发现后已撤回）。

### 验收证据（`scripts/verify_dedup_spread.py`，生效日 2026-11-16）

```
A 当天同场重复（≤1）：✅ 违规 0 篇
B 跨天同场重复（≤1）：✅ 违规 0 篇
C 同事件重复（≤2/7天）：✅ 违规 0 篇；最大事件簇 山东泰山#coach × 1
D 单主体集中（≤4篇）：✅ 违规 0 篇；最大主体簇 毕尔巴鄂竞技 × 1
E 接线（AST）：✅ fill_gap 关键字 ['date_str','exclude','stats'] / ['accept'] / _reservoir_accept 含 dedup.judge
F 负向自检：✅ dedup.apply 3 条同场只留 1 条；fill_gap 取到 0 条、拒绝计数 3
旧链路留证：65 篇 A 2 / B 4 / C 0 / D 7；最大主体簇 曼联 × 11
```

F 项是这条验收的关键：**3 条同场候选一条都补不进来**（拒绝计数 3）。只验「今天违规 0 篇」没有意义——今天本来就没跑新代码；证明闸门真的在拦，靠的是负向用例。

单测 `tests/test_dedup_supply.py` 10 例。

## 2. 改动点 2：未分类率（部分达成）

`config/topic_category.yaml` v1.0 → v1.1（生效 2026-11-16），`topic_category._FALLBACK` 同步：
赛果模式补 `崩盘|哑火|封喉|翻盘`；转会补 `帅位/接手/解雇/走人/上任/执教/卸任/转正/挂帅/盯上/引援/冬窗/夏窗/报价/转会窗`；冲突补 `反对/不满/硬刚/回击`；中国足球补 `中国球员/国脚/留洋`。

**结果：未分类 29/69 = 42.0% → 19/69 = 27.5%（同一份语料救回 10 篇）。** 14 天窗口按最新算法 75 篇：战报 36% / 未分类 28% / 中国足球 19% / 转会 16% / 冲突 1%，目标 ≤20% **未达成**，仍是告警项。

残留未分类主要是「战术观察 / 里程碑纪录 / 人物 / 数据对比」——五类轴装不下。**不硬扩**：扩轴要同步改 `ratio_config` / `ratio_tuner` / 看板，属单独立项，这次不动。

### 反直觉发现（影响后续判断）

| 战报比分 | 25 | 20 | 192 | 58777 | **0.33%** |
| 未分类 | 22 | 13 | 1506 | 55242 | 2.73% |

## 3. 改动点 3：配比守卫（软闸门）

`mix_guard.py`（新，约 200 行）：`load_targets()` 只读 `config/ratio_config.yaml` 的 `选题类型配比`（读不到返回 None）；`ledger_counts()` 只读**日期级** `publish_ledger_<date>.json`（metadata 是覆盖写，拿它当分母系统性高估；混入 `_morning/_noon/_evening` 会让 total 虚高约 1.9 倍）；`check()` 叠加本批未发布成稿、`MIN_SAMPLE=20`、样本不足或配置缺失一律 `ok=None`。

`orchestrator.save_articles_local` 写 `metadata.mix_guard` + `metadata.mix_overshoot`。**不改一个字的发布决定**——11-11 晚间就是拿一个 CTR 指标卡发布，结果整批 0 篇。

生效日前 62 篇基线：战报 **32.3%**（目标 10%，+22.3pt）、未分类 26%、中国足球 21%、转会 17.7%（目标 30%，**−12.3pt**）、冲突 3%。生效日后仅 6 篇 → 未判定。

配合第 2 节：**战报比分拿走最多配额（36%），CTR 却最差（0.33%）**。这不是「配比不好看」，是把最大一块配额给了最差的类型——配比守卫的价值在这里，不在那个百分比本身。

## 4. 改动点 4：锚点归零——前提被数据推翻并纠偏

方案原定「把『每批必须含 1 篇数据对比』改成『有比赛日优先赛程稿』」。实测推翻了这个前提：

- 锚点归零起点是 **11-10**（当天 2/4 = 50%），不是 11-11；
- `topic_funnel.jsonl` 的 slot 层显示 **11-10~11-15 六个批次日「确定性 = 0、战报 = 0」**——国际比赛日，俱乐部赛程供给为零；
- 热点球评 24 篇里只有 5 篇有锚点，归零主因不是数据对比挤位。

所以改成：

1. **不动**「每批必须含 1 篇数据对比」（它还托着 `batch_mix` 的 data 槽，且 `tests/test_content_mix.py` 明确断言该句必须存在）；
2. `prompts/topic_selector.txt` 追加「有比赛日另须至少 1 篇写当天比赛」+「标题必须写出过程：第几分钟/连进几球/谁被换下/哪张牌/从几比几追到几比几」；无比赛日加警示「不要硬凑过程，改用出场数/进球数/身价」；
3. `orchestrator._anchor_material(topic)` 扫 `title_brief.brief_text` 是否真含过程锚点；`repick_for_anchor(...)` 只在「标题无锚点 **且** 素材里确有过程」时重写，并只接受真带锚点的结果（素材没有过程就**不许硬凑**）；
4. `_title_gate_row` 增 `anchor_kinds`（判不了写 None）与 `anchor_repick` 留证。

`verify_title_anchor.py` 新增 `check_anchor_trend(days)`（advisory）：「有赛程却连续 2 天 <20%」才告警。当前输出「未出现该组合 ✅」——因为这几天确实没赛程。**这条告警现在是「无赛程」而不是「有赛程写不出过程」，两者处置完全不同。**

## 6. 改动点 6：台账补成稿分母

### 改了什么

- 新模块 `ledger_funnel.py`（口径**唯一实现**）：`draft_snapshot()` 读当天 metadata 得 `drafts` / `dropped_compliance` / `published_with_title_gate_issue`，读不到返回 `available=False` 且**不写 0**；`lost_upstream()` 不为负时也**不截断**（为负=台账比成稿还多，是证据）；`identity()` 校验两条恒等式。
- `publisher.write_publish_ledger` / `_merge_day`：`counts` 增 `drafts` / `dropped_compliance` / `lost_upstream` / `published_with_title_gate_issue`，payload 增 `identity`。**`counts.total` 语义不变**（= 台账记录条数），不破既有断言与既有读取方。
- **单批次文件不算 `lost_upstream`**（留 None）：metadata 是当天累计、本批 records 是单批，拿两把尺子相减会造出巨大假缺口。只有日级聚合同口径才计算。
- `verify_publish_success.py` 新增：
  - **F 成稿口径成功率**（advisory，只报数）：分母 = 成稿 − 按设计跳过；
  - **G 台账恒等式**（hard）：I1 `counts.total == len(records) == Σ各 status`（直接数 records，老台账也判）；I2 `drafts ≥ total`（生效日前的日期判未判定）。

### 实测

| 口径 | 计算 | 结果 |
|---|---|---|
| A 尝试口径（旧） | 61 / (61+1) | **98.4%** |
| F 成稿口径（新） | 61 / (73+4−3) | **82.4%** |
| 若 8 篇缺口都发了（上限） | 69 / 74 | 93.2% |

缺口拆解：**8 篇「成稿在、台账无记录」，全部发生在 11-05 之前**（11-02:2、11-03:3、11-04:1、11-05:2），11-06 起为 0 —— 正是 11-04「三层写入」修复前后的分界。所以 82.4% 是**下界**，真实值落在 [82.4%, 93.2%]，不可再精确。这就是取证缺口的代价。

### 两处纠偏（方案原文需修正）

1. 方案写「从 `articles[].title_gate_blocked` 读 `dropped_gate`」——但该字段的语义是「标题结构不合格**仍发布**并留证」，这些篇已经 `published`，按丢稿计会**重复计数**并使恒等式失败。改为独立一栏 `published_with_title_gate_issue`。
2. 方案预估「同一窗口重算 88.4% = 61/(65+4)」——该分母漏了 8 篇「成稿在、台账没有」。按 metadata 成稿口径实测是 **82.4%**。

I1 恒等式在全部 47 个历史日级台账上成立（`counts.total == len(records) == Σstatus`，只有 4 种状态码在跑）。

单测 `tests/test_ledger_funnel.py` 17 例（含三条负向：未知 status 必红、成稿<记录必红、老台账无字段必须「未判定」而非通过）。

## 8. 两条现存的红项（均与本次改动无关，附证据）

| 验收 | 结论 | 证据 / 归因 |
|---|---|---|
| `verify_batch_mix` | ❌ 每批 data 槽命中：10/14 批降级 | `git show HEAD:data/audit/batch_mix_latest.json` 已是 `ok=False`（11-16 14:14 生成），**改代码前就红**。根因是「数据对比/排行榜」候选池空，属供给问题 |
| `verify_title_anchor` | ❌ 生效日累计 75 篇锚点 30.7% < 40% | HEAD 版本是 pass，但那是 11-12 生成的报告（窗口 11-05~11-12、30 篇 40.0%）。样本从 30 涨到 75 后自然掉下来，与本次改动无关（判据只读历史 metadata + `title_features`，本轮未改） |
| 恒返 rc=2 的 5 个 | 未判定 | `verify_compliance` / `fixture_pool` / `gallery_entities` / `image_relevance` / `wiki_media`——本机无证据（网络/密钥/夹具），非作废 |

**必须点明的风险**：改动点 1 让补位更保守（命中重复就不补，宁可少写不凑数），这会**加剧** data 槽降级。即 `verify_batch_mix` 可能从「10/14 批降级」变差。两者是同一件事的两面：供给不足 → 补位 → 重复。**下一步要扩「数据对比/排行榜」候选池，不是放松去重。**

## 9. 下一窗口（11-20~12-03）看什么

1. `final.补位拒绝重复` > 0 且 `data 槽降级` 同时上升 → 供给不足被去重放大了，先扩池；
2. 有赛程日的锚点覆盖率是否回到 ≥40%（`verify_title_anchor` 的逐日表；无赛程日不算）；
3. 战报比分占比是否从 32.3% 降到 ≤15%，转会是否从 17.7% 回到 ≥20%；
4. 未分类率是否 ≤20%，若仍 25%~28% 则按第 2 节结论**扩轴而不是继续加词**；
5. `chart:*` 封面 CTR 是否仍与「无封面」同档（决定数据图版式是否重做）；
6. `counts.lost_upstream` 是否恒为 0（新台账口径自愈的标志），以及 F 项成稿口径成功率是否回到 ≥85%。
