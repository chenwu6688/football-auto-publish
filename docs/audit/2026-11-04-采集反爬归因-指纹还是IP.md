# 采集反爬归因：challenge 是「指纹」还是「IP」

- 日期：2026-11-04
- 起因：上一轮评估外部项目 NewsCrawler 时发现它用 `curl_cffi` 做 TLS 指纹伪装，
  而我方全仓只有裸 `requests`。当时给的建议是先做 A/B，别直接换库。
- 本轮结论：**那 25% 的 challenge 大部分不是反爬，是我们自己的判据误报。**
  `"eo-"` 这个特征串会命中 `video-`，而直播吧每篇文章都引用 `video-player2.js`，
  于是每篇正常比赛稿（20~30KB，低于薄壳阈值）都被判成「被拦」并整篇丢弃。
  TLS 指纹那部分本机确实复现了，但它不是主线，而且生产用不上。

---

## 1. 先纠正上一轮的一个前提错误

上一轮我把「75 次请求 19 次 challenge（25%）」当成我方采集成功率在说。核了一下来源：

```
data/audit/scraper_fetch_latest.json  generated_at = 2026-11-04 12:05
记录时间 12:00:52 → 12:05:05
提交者 25e5a2b "chore: 回写 LLM 用量与软性蓄水池"（04:05:10 UTC = 12:05 CST）
```

这份台账是**午间批次（cron 4 UTC）在 GitHub runner 上跑出来的**，不是本机。
所以那 25% 是「海外机房 IP + requests」的成绩，本机成绩是另一回事——

```
本机连续 8 次 GET https://www.zhibo8.cc/：
  200 / 615,682 B / 无 EdgeOne 特征 / 中位 0.6s，8/8 全过
  本机出口 IP = 117.151.73.214（AS9808 中国移动，上海）
```

**同一个 URL、同一套请求头、同一个库，只换 IP 就换结果。** 这是本轮第一个变量。

---

## 2. 但「换 IP」不是唯一变量 —— 本机铁证

如果只是 IP 风控，那本机应该对两个站点都全过。测完懂球帝就发现不对了。

设计矩阵：**同一台机器、同一个 IP、同一个 URL、同一套最小头**，只换 HTTP 库。

| 站点 | 通道 | 结果 | 中位字节 |
|---|---|---|---|
| 直播吧 | requests + 全头（生产 `_http_get`） | 4 ok / 0 challenge | 615,688 |
| 直播吧 | requests + 最小头 | 4 ok / 0 challenge | 615,688 |
| 直播吧 | urllib + 最小头 | 4 ok / 0 challenge | 602,245 |
| **懂球帝** | **requests + 最小头** | **0 ok / 4 challenge（HTTP 567）** | **7,352** |
| **懂球帝** | **urllib + 最小头（生产 `_http_get_plain`）** | **4 ok / 0 challenge** | **310,319** |

补上 `curl_cffi` 之后的三通道对照（n=5~6，交错发请求，结果一致）：

```
A·requests（现状）       challenge 5/5 = 100%   ok 0%    中位字节 7,352
    被拦来自节点: {'TencentEdgeOne/EdgeOne': 5}
B·curl_cffi(chrome131)  challenge 0/5 = 0%     ok 100%  中位字节 316,557
C·urllib（零成本）       challenge 0/5 = 0%     ok 100%  中位字节 316,689
⇒ 结论：最优通道 urllib
   基线 requests 100% → urllib 0%，降 100%，Fisher p=0.0079；零成本
```

**关键不是「curl_cffi 有效」，而是「只要不是 requests 那套指纹就行」** ——
两条备选通道都 100% 通过，其中 urllib 是标准库、零依赖。

**这就是答案**：EdgeOne 的判定里包含 TLS/HTTP 栈指纹，不只是 IP。
四个条件（机器、IP、URL、头部）全相同，唯一变的是「用哪个库发请求」，
结果从 100% 被拦翻到 0%。

顺带解释了生产台账里懂球帝 ok 17 / challenge 2：`_http_get_plain` 本来就用 urllib，
所以它一直是对的；那 2 次是抖动（UA 轮换或边缘节点差异）。

## 3. CI 实测：三通道 150 次请求，一次都没被拦

先按原计划在 runner 上跑（`ubuntu-latest` + py3.11，与生产同环境）：

```
直播吧 www.zhibo8.cc  每组 50 次，耗时 268s
  requests    0/50 = 0%   ok 100%   中位 615,781B
  curl_cffi   0/50 = 0%   ok 100%   中位 615,781B
  urllib      0/50 = 0%   ok 100%   中位 615,781B
懂球帝 dongqiudi.com  每组 50 次，耗时 204s
  requests    0/50 = 0%   ok 100%   中位 316,799B
  curl_cffi   0/50 = 0%   ok 100%   中位 316,799B
  urllib      0/50 = 0%   ok 100%   中位 317,018B
```

**一个都没拦。** 包括本机 100% 被拦的「懂球帝 + requests」。

这说明两件事：① 那 25% 不是稳定特征，换库的收益无从谈起；② 探针测的是首页，
而首页在台账里本来就是 2/2 ok —— **我把目标打错了**。

## 4. 真因：不是反爬，是我们自己的判据误报

回到台账看那 19 次 challenge 到底发生在哪个 URL：

```
challenge 19 次的 URL 形态：match 页 12 + news 列表页 5 + 懂球帝某篇 2
ok       56 次的 URL 形态：match 页 34 + 首页 2 + 懂球帝首页/文章 17
```

17 次落在 `news.zhibo8.com/zuqiu/.../matchXXX.htm`。**而首页一次都没被拦。**

拿其中一个 URL 实测，三条通道全 100% 被判「挑战页」，本机也一样：

```
https://news.zhibo8.com/zuqiu/2026-11-04/match2272728date2026vnative.htm
  requests / curl_cffi / urllib   各 5/5 challenge，中位 25,523 字节
```

### 直接看内容

```
HTTP 200，25,523 字节
<title>让二追三！曼城3-2绝杀，库里尼亚3分钟2球导演逆转</title>
去标签后正文 9,562 字
```

**这是完整的正常文章。** 为什么被判成挑战页？把特征串逐个对照：

```
命中 'eo-' @1614: ...static4style.duoduocdn.com/news/js/video-player2.js...
```

`video-player2.js` 里 **`video-` 包含子串 `eo-`**。而文章页 20~30KB，
低于 `CHALLENGE_MAX_BYTES = 60_000` 的薄壳阈值 → 两个条件同时满足 → 判挑战页。

**直播吧每篇文章都引用这个播放器脚本**，所以每一篇正常比赛稿都被判成「被反爬拦」，
抛 `ScraperChallengeError`，整篇丢弃。

### 为什么首页逃过了

首页 615KB > 60KB 阈值 → 直接被字节数挡住，永远不会判 challenge。
所以「首页能抓、文章页抓不到」这个现象一直存在，只是被记成了「反爬」。

### 真挑战页靠什么命中

懂球帝 567 页（7,351 字节）真实内容是：

```
若您是网站拥有者，请参阅 EdgeOne Web 安全分析官方文档，了解如何筛选请求 ID …
```

命中 `EdgeOne`，**不需要 `eo-`**。这条串短得像「猜的」，实际从没起过作用，
只贡献了误报。

### 修复与验证

从 `CHALLENGE_MARKERS` 删掉 `"eo-"`，并留下一条「不要再加回来」的注释。

```
直播吧真实文章页 (25,523B):  challenge=False   ← 修复前 True
直播吧真实文章页 (22,379B):  _http_get 成功返回 22,379 字符  ← 修复前抛异常
懂球帝真实挑战页 (7,351B, HTTP 567): challenge=True   ← 无漏报
```

单测加两条，一条守误报（`video-player2.js` 的页面不许判挑战），
一条守漏报（真 EdgeOne 文案必须仍判挑战）——**修误报最容易顺手引进漏报**，
必须两条一起守。

### 影响面

台账 75 次请求里 19 次 challenge，**17 次是误报**。真实采集成功率不是 73%，
而是接近 97%。而丢掉的正是「比赛稿」这一类——它恰好是 `topic_funnel` 里
`llm` 候选偏少、`batch_mix` 常常填不满的上游之一。

**这一类 bug 的性质**：判据没坏（它一直在老实干活），坏的是判据里的一个短串。
短串比漏报危险得多——漏报是「没抓到」，误报是「抓到了却当成没抓到」，
而且它会在台账里长得和真反爬一模一样，让人往完全错误的方向查了一整轮。

## 5. 那 TLS 指纹那一节还有意义吗

有，但不是现在用。它证明的是「同一 IP 下换 HTTP 栈能改变 EdgeOne 的判定结果」
（第 2 节，p=0.0079），这条结论本身成立、可复现。但它只在一个**真实存在**
的拦截场景下才用得上，而目前生产上唯一真实的拦截场景（懂球帝 567）
`_http_get_plain` 本来就用 urllib 绕过了。

所以 `curl_cffi` **不引入**。留着探针，下次真遇到「换栈就能过」的站点时，
一条命令就能验证，不必重新发明。

## 6. 交付物

### `scripts/ab_fingerprint_probe.py`

三通道**交错**发请求（不是先跑 50 次 A 再跑 50 次 B——那样后一组承受更高累计请求量，
看起来天然更差）：

| 通道 | 实现 | 意义 |
|---|---|---|
| A `requests` | 与 `_http_get` 完全同头 | 生产现状，基线 |
| B `curl_cffi` | `impersonate=chrome131` | 换 TLS 指纹（要装依赖） |
| C `urllib` | 与 `_http_get_plain` 同路径 | **零成本备选** |

四个细节值得说明：

- **判据复用 `scraper_diagnostics`**（`classify_status` / `looks_like_challenge`），
  不另立一套口径。否则测量用的尺子和生产用的尺子不是同一把。
- **探针请求绝不写生产采集台账**（单测用 AST 查真实调用守着）。100 次探针混进
  `scraper_fetch` 会把「采集成功率」这个指标污染掉。
- **记录响应侧节点信息**（`Server` / `eo-log-uuid` / `cf-ray`）：如果 ok 和 challenge
  来自不同节点，说明是边缘分流而不是指纹判定——这两种成因的处置方式完全相反。
- **同分优先零成本通道**（`COST_RANK = {"urllib": 0, "curl_cffi": 1}`）：本机实测
  urllib 与 curl_cffi 都是 0%，若只按 challenge 率取 min，会按字典顺序挑到
  curl_cffi —— 那就等于白引一个依赖。判据里写死成本序，并有单测守着。

退出码按项目契约：`0` 有结论 / `1` 参数错误 / `2` 未判定（环境不复现或缺依赖）。
「测不出问题」返 2 而不是 0，是为了防止它被读成「验证通过」。

### `.github/workflows/fingerprint-probe.yml`

手动触发（`workflow_dispatch`），`runs-on: ubuntu-latest` + Python 3.11——**与
`batch.yml` 完全同环境**，因为换 runner 就换了 IP，测出来就没意义。

跑两段：直播吧（全头）+ 懂球帝（最小头），结果回写 `data/audit/fp_probe_*.json`
（本机 pull 就能看，不必去 Actions 页面翻日志）+ 上传 artifact。

**这里踩过一个 CI 才暴露的坑**：顶层 `env` 引用 `${{ inputs.n }}` 只在
`workflow_dispatch` 下有效，而它还要被 push 触发；push 时 `inputs` 上下文不存在，
整个 workflow 直接求值失败、一段探针都跑不起来 —— 而失败只出现在 Actions 页面，
本机只看到「推了但 data/audit 里没有结果文件」。改用 `github.event.inputs.* || 默认值`。

### `tests/test_ab_fingerprint_probe.py`（18 项）

判据自己必须有单测，否则就是拿一把没校准的尺子去量，再按量出来的结果改生产代码。
其中 `fisher_p` 用「茶与牛奶」实验对标教科书值（`[[3,1],[1,3]]` → 双侧 p = 34/70）。

**下一步该看的是「修复后稿量有没有变化」**：如果之前每天被误判丢掉一批比赛稿，
修完之后 `scraper_fetch` 的 challenge 率应该从 ~25% 掉到接近 0，
同时 `topic_funnel` 的 `llm` 候选数和成稿数应该上升。
这两个数一起看，才能确认这次修复真的转化成了稿量——单看 challenge 率下降
也可能只是「判据变松了」，而判据变松是会骗人的。

## 8. 未验证项（必须说清楚）

1. **修复对稿量的实际影响** —— 需要等下一批真实运行。判据是「challenge 率下降
   **且** 成稿数上升」，只降 challenge 不涨稿，说明有别的地方在丢稿。
2. **除 `eo-` 外还有没有同类短串**：`"安全验证"`、`"访问验证"` 这类中文串理论上
   也会被正常文章命中（比如讲「需要安全验证」的稿子）。本轮只根除了已被证实的
   `eo-`，其余没找到实例，也没动——**没有证据的放宽和没有证据的收紧一样危险**。
3. **GitHub runner 的出口 IP 每次不同**（Azure 段池），单次探针有波动；
   若结论卡在临界（比如 p=0.06），应重跑 2~3 次再定，不要拿一次结果下结论。
3. **本机装 `curl_cffi` 用了 9 分 24 秒**（14MB wheel，104 kB/s，且它顺手把
   certifi 从 2026.7.22 升到 2026.10.23）。装上后跑通了，结果是 0/5 被拦。
   这也说明：在 CI 里装它不算负担，但在本机装一次很慢。
5. **`/tmp` 是 10MB tmpfs** —— pip 默认拿它当临时目录会报 `Errno 28 设备上没有空间`。
   装包时要 `TMPDIR=/home/chenwu/.workbuddy/tmp`。这条已记进项目备忘。
