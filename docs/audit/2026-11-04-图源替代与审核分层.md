# 图源替代与审核机制分层（2026-11-04）

承接两件事：① 用户问「有没有国内可用的免费图源」；② 用户要求「结合头部账号特点重新梳理审核机制，并把上轮新想到的三点落下来」。

---

## 一、图源：国内没有开放 API 的免费正版图库，但手上有一条更好的路

### 1.1 实测（本机直连 + 走代理各一次，2026-11-04 13:0x）

| 图源 | 直连 | 走代理 | 判定 |
|---|---|---|---|
| `zh.wikipedia.org` / `commons.wikimedia.org` | 超时 10s | ProxyError | **不通**（不是慢） |
| `api.openverse.org` | 超时 10s | — | 不通 |
| `api.unsplash.com` | 401 | 401 | 域名可达，**应用 In review / Key 未生效** |
| `images.unsplash.com` | 404 | — | 域名可达（图不存在才 404）→ **CDN 是好的** |
| `api.pixabay.com` | **400** | **400** | **可达**（400 = Key 无效，不是网络问题） |
| `api.pexels.com` | **401** | — | **可达**（401 = 未认证） |
| `pixabay.com` 网页 | 403 | 403 | 网站被 Cloudflare 挡（≠ API 不通，别混淆） |
| `image.baidu.com` / `pic.sogou.com` | 200 | — | 可达，但**无开放检索 API** |
| `tuchong.com` / `ssyer.com` | 200 | 200 | 可达，但**无开放 API**，抓取有版权与稳定性双重风险 |

结论：
- **国内没有一个对外开放检索 API 的免费正版图库。** 图虫、沙沙野、百度/搜狗图片都是「网页可达、API 不存在」，爬取它们等于把版权风险和反爬风险同时引进管线，不做。
- Pixabay / Pexels 虽是国外站点，但 **API 域名从本机与 GitHub Actions 出口都通**，且注册即用、**无需审核**（对比 Unsplash 的 5–10 个工作日）。

### 1.2 真正的答案是「新闻源正文图」，而且它一直躺在代码里

`media_scraper.scrape_match_report()` 抓直播吧战报时，已经把正文 `<img>` 抽成了
`fixture["source_images"]`。但全项目只有 `_find_source_article()` 那一条路径消费过它，
**其余 6 处 `img_topic` 都是从 LLM 产出重建的，根本拿不到这个字段** —— 抓了等于没抓。

这条链路的精度高于任何图库：它就是那场比赛的图，图文天然一致、零网络请求、零 Key、
不新增版权风险（转述性引用新闻源配图）。所以放到配图链路的最前面：

```
⓿ 新闻源正文图（零成本，精度最高）
① 手工实体精确页 → ② 实体词典 → 维基搜索（本机/CI 均不通，熔断跳过）
③ Pixabay（5000/h 免审核）→ Pexels（200/h 免审核）→ Unsplash（等审核）
④ 全断时：cover_card 原创数据卡（1200×675）
```

改动：
- `data_collector`: 新增 `_gallery_pixabay()` / `_gallery_pexels()`；`search_images()` 增加 ⓿ 层。
  两家都要求 query 绑定正文实体（计划 2.2 禁用随机图库），且**无 Key 时不再静默跳过**，
  按 `scraper_diagnostics` 落账（`kind=empty`，detail 写明「注册即用，无需审核」）。
- `orchestrator._img_topic()`: 把候选对象里的 `source_images` 透传给 6 处调用点。
- `cover_binding.image_is_bound()`: `news_source` 加入「按实体/事件精确抓取」白名单。
  否则它会被「query 是否通用」这条检索侧规则误杀——那条规定是为图库设计的，用在新闻源图上属于错配。
- `scripts/probe_image_sources.py`: 探活项从 4 条扩到 7 条，新增新闻源链路的功能级探测
  （直接喂一张假图给 `search_images`，看它有没有被消费）与 Pixabay/Pexels 的 Key 状态区分。

### 1.3 需要你做的（两件，都只要几分钟）

1. **Pixabay Key**：`pixabay.com/account/api-key` → 填入 `scripts/local_env.sh` 的 `PIXABAY_KEY`
   与 GitHub Secrets。**无需审核**。（注意：pixabay 网页从国内常 403，但 api 域名是通的。）
2. **Pexels Key（可选）**：`pexels.com/api` → `PEXELS_KEY`。额度只有 200/h，作备选。
3. Unsplash 那个应用继续等审核即可，代码已就绪，Key 一有效立刻生效。
   **Secret key 不要入库**（只调公开读接口，用 Client-ID 就够），截图里那个已外泄，建议 rotate。

## 二、头部账号特点：区分度不在「对比」，在「数字」和「有没有意外」

用 `data/audit/benchmark_raw/*.txt` 里的 181 条图文样本（阅读中位 616）复算：

| 维度 | TOP30 | BOT40 | 差 | 判读 |
|---|---|---|---|---|
| **数字** | 90% | 49% | **+41** | 最强单维 |
| 冲突/反常 | 57% | 44% | +13 | 有增量，方差大 |
| 过程锚点 | 10% | 2% | +8 | 弱 |
| 专名 | 93% | 90% | +3 | 几乎无区分（人人都有） |
| **对比** | 30% | 30% | **0** | **零区分度** |
| 疑问收尾 | 3% | 2% | +1 | 头部全场 3%，我方 11-02 后 29% |

四象限（数字 × 对比，专名=有）：

| 组 | 篇数 | 中位阅读 | ≥1000 阅读占比 |
|---|---|---|---|
| 数字=有 对比=有 | 49 | 790 | 46.9% |
| 数字=有 对比=无 | 78 | 864 | **46.2%** |
| 数字=无 对比=有 | 1 | 24 | 0% |
| 数字=无 对比=无 | 40 | 84 | 12.5% |

**「对比」加不加，爆款率一模一样（46.9% vs 46.2%）。** 这说明上轮 P0-1 把「对比」与「数字」
当成等价的两个要素，是不成立的——真实生效的是「数字」。

但也**不能改成「必须含数字」**：那 40 篇「数字=无」里躺着全场第一（54,000 阅读，
「西甲主席特巴斯斥责姆巴佩并公开致歉：绝不容许个人行为损害大局」）。
那一组是双峰的：多数很低（中位 77），但顶部极高。硬要求数字会把这个爆款形态直接判死。

所以本轮**不动三要素阈值**（三要素合计的区分力是好的：TOP30 通过 83% vs BOT40 48%），
只把结论记下来，避免下次又有人把「对比」当作硬指标加码。另外顺手否掉一个假设：

> **专名密度不是信号**。0 个专名中位 933，1 个 735，2 个 260，3+ 个 612 —— 不单调。
> 「多塞几个队名」既不加分也不该加分。

以及一条之前不知道的事实：**质疑收尾/疑问收尾在头部占 3%，我方 11-02 后是 29%**，
限额 14 天 ≤2 篇（≈7%）**偏松而不是偏严**。上轮我一度按「中位阅读无差」判它过严，
那是拿 88 篇老稿的小样本外推，错的方向。

## 三、审核机制：从「一层平铺」改成四层，并且审审核本身

### 3.1 原来的问题（都有实证，不是感觉）

1. **39 个验收一视同仁地每周一跑一次**，而绝大多数在验「代码接没接 / 常量自不自洽」——
   这是开发期一次性的事。真正该天天看的（发出去几篇 / 失败没有 / 有没封面 / 有人点没有）
   一个硬门禁都没有：11-04 一天 2 篇 1 成 1 败（发布超时: 无API响应），零告警。
2. **8 个发布前验收里 7 个带 `|| echo`**：FAIL 了稿子照样走到「发布到头条号」。
3. **有 3 个验收写了却从没被 CI 跑过**：`check_slot` / `ranker_signals` / `test_gate`。
4. **有恒真的判定**：`verify_publish_gate` 复算标题时不传 `recent_titles`，
   「疑问收尾 14 天 ≤2 篇」从来没触发过，每次都判「合规 ✅」。

### 3.2 新的分层（`config/audit_tiers.yaml`，39+1 项全部登记）

| 层 | 什么时候跑 | 语义 | 项数 |
|---|---|---|---|
| **pre-publish** | 每批发布前（batch.yml） | FAIL 挡不挡**这一批**发布 | 8 |
| **daily** | 每天 08:10 CST（`daily-result.yml`） | 看「昨天真的发生了什么」，红了必须有人看 | 12 |
| **code-change** | 代码/Prompt/配置变更（`plan-invariants-verify.yml`） | 口径类，只在变更时才有新结论 | 17 |
| **weekly** | 每周一（`weekly-audit-health.yml`） | 慢变指标 + 元验收 | 5 |

两条设计取舍：

- **发布前硬阻断只保留 1 项**（`content_mix` 的禁发类型）。`batch_quota` 一度也想做成硬阻断，
  但它内含「decide 冒烟」等 5 个子项，抖动一次就把当天剩下所有批次全停掉——
  收益（少发 1 篇）远小于代价（当天 0 篇）。真正不可撤回的只有「禁发类型」，其余都降为告警。
- **`kind` 只表示「挡不挡发布」，不表示「CI 里会不会红」**。每日门禁的步骤都不带 `|| echo`，
  红了就是红了，但那不等于要停发。两件事混着谈，就会得出「7/8 只告警所以没人管」这种
  既对又不解决问题的结论。

### 3.3 三个新思路的落点

**① 验收器必须有负向用例 → `scripts/verify_audit_health.py`（元验收，每周硬项）**

判据是「**能不能报红**」而不是「当前是不是绿」。六项：

| 项 | 内容 |
|---|---|
| 清单完整性 | 脚本 ↔ 清单**双向**一致：漏登记（有人加了验收没说什么时候跑）/ 幽灵项（清单独自美丽）|
| 负向用例债务 | 无边向用例的项数 **≤ baseline_negative_debt（31）**，只许降不许升 |
| 硬项接线与阻断 | `kind: hard` 必须真被调用；`pre-publish` + hard 不得带 `|| echo` |
| 每日层最小集 | `required_daily` 6 项不得被移出 daily（防「每日门禁」被慢慢掏空）|
| 元层负向自检 | 把 baseline 调低 1，上一项**必须**变 FAIL —— 否则元验收自己也是恒真的 |
| 产物落盘 | 每项都要写 `data/audit/*.json`，否则结论只活在 CI 日志里 |

为什么不一次要求 39/39 都有负向用例：那会让这条线立刻变红，**红久必被 `|| echo` 软化**
（11-03 的坑）。改成「债务只许降」，现在 9/40 有负向用例、31 项在还债，数字照实写进报告。

**② 频率反转 → 两个新 workflow + 一个改触发**

- 新增 `daily-result.yml`：每天 08:10 CST，跑结果类硬门禁（发布成功率 / 封面 / 结构 / 配比 /
  标题硬违规 / 效果闭环 / LLM 额度），并在 Step Summary 里出汇总表。
- 新增 `weekly-audit-health.yml`：每周一元验收 + `test_gate` + 两个「死脚本」。
- 改 `plan-invariants-verify.yml`：新增 `push/pull_request` 的 `paths` 触发（`**.py` /
  `config/**` / `prompts/**`），保留每周兜底。改动当天就能发现回归，而不是等下周一。

**③ 单一尺子 → 上轮已收敛，本轮补上防复发**

上轮把保存阶段的 `_title_score`（给问号 +2 分）改成调 `score_title_plan`，
消除了「保存侧奖励问号、闸门拦问号」的对撞。本轮不再动评分权重（三要素合计区分力是好的），
改成让**清单机制**兜住：新增任何标题验收都必须登记 `tiers` / `kind` / `negative`，
否则元验收的「清单完整性」直接红。漏登记 = 加不进来。

## 四、元验收跑出来的东西（这才是它的价值）

第一版跑出来不但不是全绿，还抓到了三个真问题：

1. **扫描器漏判 YAML 续行**。首版只判断「本行剩余为空」才看下一行，
   而 `batch.yml` 里是 `verify_xxx.py --quiet \` + 换行 + `|| echo` →
   它报出「发布前被软化 0 个」，而实际上 `batch_quota` 就是被软化的。
   **是单测 `test_hard_wired_fails_when_prepublish_softened` 抓到的**，不是我看出来的。
2. **3 个死脚本**：`check_slot` / `ranker_signals` / `test_gate` 从没被 CI 调用，
   已全部接进 `weekly-audit-health.yml`。
3. **债务基线**：实测 40 项里只有 9 项有负向用例，其余 31 项「恒真风险」，写进 baseline。
