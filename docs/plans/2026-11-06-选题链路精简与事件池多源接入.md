# 选题链路精简与事件池多源接入 · 实施计划

- 日期：2026-11-06
- 背景：2026-11-06 两次事故（配图验收误判致 noon 0 篇、选题不跟热点且同场重复发）修复后，
  用户要求在此基础上**精简链路、去除冗余环节**，并把热点池从「热搜榜单源」扩到主流足球媒体。
- 依据：`data/audit/topic_funnel.jsonl`（11-06 晨读/午间两条原始记录）、
  `data/audit/media_sources_2026-11-06.json`（本计划新增的源探测基线）、
  `output/2026-11-0{5,6}/metadata.json`。
- 一句话结论：**链路的问题不是"源不够多"，是"同一件事写了好几处"**。先收敛重复定义，
  再加源；顺序反过来只会让重复的地方多一倍。

## 一、现状复杂度的量化台账

「冗余」不能凭感觉说，下面每一条都能指出具体文件和具体行数意义上的重复。

| # | 同一件事 | 写在哪几处 | 后果（已发生的） |
|---|---|---|---|
| 1 | **供给入口** | `select_topics`(LLM) / `_hot_topic_cards`(board) / 同函数降级(news_cluster) / `collect_recap_topics` / `collect_fixture_topics` / `_add_event_result_articles` / `deterministic_supply.fill_gap` / `event_cluster` + reservoir 兜底 = **8 个入口** | 每个入口各自算配额、各自去重、各自留痕；「一篇稿从哪来的」要读 5 个文件才能答 |
| 2 | **一事件多角度** | `_add_event_result_articles`（揭晓型）、`deterministic_supply`（节点）、`event_cluster`（S 级） | 三套判据、三套上限，都是「一个事件写多篇」，互相不知道对方写过 |
| 3 | **去重** | `select_topics` 内连做 5 道：批内(50%) → 跨批(标题/关键词40%/事件指纹/对阵) → 昨日(40%) → 7 天指纹 → 7 天关键词(50%) | 漏斗只能记「去重共吃 0 条」，分不清是哪一道；弱判据（关键词集合）既漏又误杀 |
| 4 | **重排** | `topic_category.prioritize` → `ranker`(L1/L2/L3 五维) → `batch_mix.assign` = **同一批候选被排三次** | 三次各有自己的顺序语义，最终顺序谁都说不清；L3 花 LLM token 排完后 `[:1]` 只写 1 篇 |
| 5 | **内容类型** | `content_type`（11 类，`content_mix.TARGET_PCT`）／`板块`（转会动态·人物故事·中国足球·战术榜单，fixture 用）／`topic_category`（转会官宣·冲突舆情·中国足球·战报比分·未分类） | 三套轴互不映射；`数据对照` 只在 fixture 和 `awareness_gate` 出现，`TARGET_PCT` 里没登记 → 未登记类型 |
| 6 | **类型上限** | `content_mix.TARGET_PCT`（月度占比）与 `batch_mix.DAILY_CAP`（单日篇数） | 两处都在表达「这类一天最多几篇」，改一处不改另一处就互相打架 |
| 7 | **篇数额度** | `constants.BATCH_QUOTA` ／ `config/ratio_config.yaml`（日更篇数+时段权重）／ `config/config.yaml` = **三处镜像** | 已有 `verify_batch_quota` 兜底，但仍是「改一处忘两处」的定时炸弹 |
| 8 | **实体词表** | `constants.WIKI_TEAMS`（15 队）／ `config/entity_map.json`（709，A75/B198/C436）／ `config/player_names.json`（131 人） | **C罗、梅西、萨拉赫不在 entity_map** → `awareness_of` 返回 `"?"` → L1 直接 block。这是「C罗退役」进不来的直接原因之一 |
| 9 | **认知度** | `awareness_gate`（硬门槛）与 `entity_map.awareness` 字段 | 球员表没有 awareness 列，球员永远判「未登记」 |

**一句话**：不是环节多，是**同一个决策点存在多个实现**。加源解决不了这个问题，
反而会让每一处重复都多一份输入。

## 二、目标架构：3 条流 / 2 道闸门 / 1 张表 / 1 套打分

```
                ┌─ 事件流 Event ── 实体 + 事件族 + 热度 + 支撑报道
   provider ────┤   来源：热搜榜 / 贴吧 / 懂球帝 / 新浪 / …
   （可插拔）    │
                ├─ 赛程流 Fixture ── 一场比赛（前瞻 / 战报 / 事件结果）
                │
                └─ 存量流 Stock ──── 节点预生成 / 蓄水池（兜底，不再新增入口）
                            │
                    ┌───────┴────────┐
                    │  闸门 G1 去重   │  对阵键（球队集合） + 事件键（实体#事件族）
                    │  闸门 G2 时效   │  发布日 < now；新闻 pubDate ≤ N 小时
                    └───────┬────────┘
                            │
                    ┌───────┴────────┐
                    │ config/slots.yaml │  唯一配额表：每日各类型篇数 + 优先级 + 单日上限
                    └───────┬────────┘
                            │
                      select_by_quota（一次排序，不再三次重排）
```

四条设计原则：

1. **一条流一个入口**。事件流无论接多少源，对下游只有一个 `EventCandidate` 结构。
2. **一个判据一个实现**。去重只认「对阵」和「事件键」；关键词重叠降级为告警。
3. **一个数字一个出处**。篇数、类型配额、单日上限全部来自 `slots.yaml`，其余模块只读不写。
4. **源失败不阻断**。provider 独立超时、独立熔断、独立台账；一个源挂了不影响其它源。

| **k7 体育** | — | ❌ **检索不到正规新闻站**；命中的结果均为博彩平台 SEO 页面 | — | **剔除（待确认域名）** |

### 关于 k7 体育与两条剔除项

- **k7 体育**：检索（含中英文）只返回博彩平台品牌的 SEO 软文，没有可核实的新闻编辑部与栏目结构。
  把它作为内容源有两个问题：素材本身是营销页、且博彩类内容在头条号属高风险。
  **若无确切新闻域名，建议直接剔除**；如你有准确地址，给我域名我按 probe 脚本再验一次。
- **球天下**：Cloudflare JS 挑战，除非引入 headless（成本高、且容易被判爬虫），否则拿不到。
- **Goal 中国**：站点本身可用，但年龄门 + 博彩广告同页，且英文标题需要翻译链路。
  留 P3，只在「其余源都不足」时评估。

### 一个反直觉的结论

**接入新源之前，懂球帝已经把昨天的热点抓到了**——`scrape_dongqiudi_headlines()`
返回的第一条就是「C罗自宣退出葡萄牙国家队」。它没进正文，不是因为源不够，
而是因为①这条素材没有进入热点池、②即使进了，`C罗` 在 `entity_map` 里未登记会被 L1 拦掉。

所以本计划的顺序是：**先修「已经有了却没被用上」的，再加新的**。

## 四、分阶段实施计划

总工时约 **6.5 人日**（不含 3 天观察）。每阶段独立可回滚，且都有对应验收脚本。

### 阶段一 · 止血与立规矩（0.5 人日，P0）

目标：把「候选 4 条 → 成稿 1 篇」的账修平，并让已有素材能真正进正文。

| 任务 | 动作 | 文件 |
|---|---|---|
| T1.1 槽位账 | `batch_mix.assign` 的 `count` 改为 `max_articles − 确定性预算`；或把 fixture 选题生成提前到结构定档之前。二选一，优先前者（改动 3 行） | `orchestrator.py` |
| T1.2 实体补登记 | `player_names.json` 并入统一 registry，补 C罗/梅西/萨拉赫等高频球员；未登记主体从 `block` 改为「打回选题侧换主体 + 落 `data/team_map_pending.json`」 | `awareness_gate.py`、`config/` |
| T1.3 时效闸门通用化 | 任何新源接入前必须过 `pubDate`／发布日校验（probe 脚本已实现 `stale` 判词） | `scripts/probe_media_sources.py` ✅ 已完成 |

| 任务 | 动作 |
|---|---|

| T3.5 事件聚合 | `event_pool/aggregate.py`：同 `event_key` 的多源条目合并为 1 条候选，热度分 = f(榜位, 讨论量, **报道源数**)；支撑报道保留多篇 |

### 阶段四 · 配额单表 + 排序收敛（1.5 人日，P1）

目标：三次重排合成一次；篇数与类型配额只有一个出处。

| 任务 | 动作 |
|---|---|
| T4.1 配额表 | 新建 `config/slots.yaml`：每日各类型篇数 / 优先级 / 单日上限 / 每批结构。`constants.BATCH_QUOTA`、`ratio_config.yaml`、`content_mix.TARGET_PCT`、`batch_mix.DAILY_CAP` **全部改为从这里派生** |

## 六、风险点与对策

| # | 风险 | 影响 | 对策 |
|---|---|---|---|
| R1 | **境外 runner 访问国内源失败** | 热点整体空转，且看不出来 | provider 独立超时 3s、失败计数入台账；连续 3 次全败自动熔断该源并告警；热点不依赖单一源 |
| R2 | **反爬升级**（贴吧曾 403、球天下 Cloudflare） | 源突然不可用 | 移动 UA + Referer 兜底；`blocked` 与 `empty` 分判词；熔断后不再重试死路 |
| R3 | **旧闻新发**（新浪 RSS 是 2018 死档） | 触碰项目红线 | 所有源强制过 `published_at` ≤ N 小时；无时间字段的源**默认不收**；probe 脚本已内置 `stale` |
| R4 | **贴吧 UGC 事实性** | 用吧友爆料当事实 → 编造 | 贴吧只作**热度信号**（进候选排序），**绝不作为事实底本**；正文事实仍取自有编辑的媒体源 |
| R5 | **博彩/合规**（k7 疑似博彩、Goal 有年龄墙+博彩广告） | 平台处罚风险 | 域名白名单；博彩类不带入；Goal 留 P3 并需合规评审后启用 |
| R6 | **版权** | 侵权 | 各源只取「标题 + 链接 + 短摘要」作选题线索；正文改写仍以既有源报道为底本；**不转载、不去水印**（《著作权法》53 条(7)） |
| R7 | **结构改造引入回归** | 发布中断 | 每阶段独立提交、独立可回滚；旧链路保留开关 1 周；`py311 compileall` + 全量单测为每次合并的硬门禁 |
| R8 | **配额表迁移漏改** | 三处镜像再次漂移 | 一次性迁移脚本 + `verify_slots_single.py` AST 硬项；迁移当日在 CI 跑一遍全量验收 |

## 七、明确不做的事（边界）

1. **不做 headless 浏览器**。腾讯/虎扑留 P2 等 API；为 2 个源引入浏览器依赖不划算。
2. **不接博彩类源**（k7 待确认域名；确认是博彩站则永久剔除）。
3. **不把贴吧/热搜当事实底本**。它们只回答「今天大家在谈什么」，不回答「发生了什么」。
4. **不砍认知度门槛**。它挡住的是「C 级实体 + 78 篇欧冠 852 阅读」的老路；
   本次只做「补登记 + 改处置方式（打回而非整条拦截）」，不做删除。
5. **不为凑篇数发低效类型**。配额表只决定「上限」，候选不够就少写。
